# PicoSerDe 格式能力规格（Format Capabilities Spec）

- **日期**：2026-10-25
- **基线**：`84a9560`（`main`，工作树 clean）
- **状态**：草案 —— **待拍板 D1/D2/D3**（见 §5），签字后进入 §9 的实施阶段
- **方法**：55 个「形状 × 格式」探针（构建期诊断采集 + 往返实测），逐格记录实际输出；不引用任何既有文档的说法
- **契约**：`picohex-picoserde`（AOT / 零反射 / fail-loud）+ `picohex-self-review`

## 1. 目的与非目标

### 目的
把「**哪种形状在哪种格式可表示**」这件事，从目前散落在 25 处 `if (formatTag == ...)` 的**隐式共识**，变成**一张可审阅、可测试、唯一的表**。

### 非目标
- 不追求「所有格式支持所有形状」（那是 §2 规则要否定的）。
- 不在本规格内解决 reader 的流式状态机差异。
- 不改变「写侧省略 null 成员」的既有设计（往返保真），除非 D1b 另行签字。

## 2. 规范性规则

> **R1（忠实编码）**：一种形状在某格式不受支持，当且仅当**不存在忠实编码** —— 即不存在一种该格式的表示，能被该格式的**合规 reader** 往返成同一个值。
>
> **R2（无静默）**：任何未进入生成代码的成员，**必须**伴随构建期诊断（`PICOSERDE003` 递归 / `PICOSERDE004` 不可表示）。
>
> **R3（不可表示 ≠ 不可编译）**：任何被判定为不可表示的形状，**不得**产出不可编译的生成代码。

**术语**
- *形状*：C# 类型在序列化视角下的形态（`List<int>`、`List<List<Dto>>`、`HashSet<T>`、递归引用……）。
- *忠实编码*：往返后值等价（元素个数、顺序、null 位置、数值文本精度均保持）。
- *不可表示*：不存在忠实编码（由 R1 判定，需给出语言层面的理由）。

**R1 的推论（重要）**：判定「不支持」时**禁止**以「我们还没实现」为理由。当前代码里多处「不支持」实际是**实现门槛**（例如扩展集合被硬编码为 `format == "json"`），必须按 §4 归为缺陷，而不是能力边界。

## 4. 缺陷清单（**不是能力取舍，必须修**）

以下四条违反 R2 或 R1 的推论，属实现缺陷。**已确认的起点**：`TypeKindResolver.Resolve` 的扩展集合分支被 `if (format == "json")` 限制（`TypeKindResolver.cs:71`），所以非 JSON 格式下 `HashSet<T>` 掉进「嵌套复杂类型」兜底分支、被解析成 `"object"`（`TypeKindResolver.cs:174-200`，因 `HashSet<T>` 有公开实例属性）。

**该成员随后在哪一步被丢弃，尚未追踪到具体代码行** —— 可由两支解释（提取期某处 `continue` 无诊断，或生成器 object 分支发射空内容），Step 0 期间必须定位到行并记录在这里。这是本规格目前**唯一**未闭环的机制细节。

| ID | 缺陷 | 证据 | 违反对应规则 |
|---|---|---|---|
| **D-1** | `HashSet<T>` 家族（`hashset/queue/stack/linkedlist/immutablearray/memory/readonlymemory`）作**成员**时，MsgPack/TOML/YAML/INI 静默丢弃 | S7：四个格式输出只有 `K`，`V` 消失，无诊断；JSON 正常 | R2 |
| **D-2** | 同上作**元素**时，MsgPack/TOML/YAML/INI 静默丢弃（JSON 报 004，其余静默） | S8：json ⛔004，其余四格式静默消失 | R2 |
| **D-3** | `Dictionary<string, List<T>>`（字典值为集合）在**全部 5 个格式**都被丢弃 —— 包括本可轻松表达的 JSON/MsgPack/YAML | S10 五个格子全 ⛔004 | R1 推论（这是「还没实现」，不是不可表示） |
| **D-4** | YAML 递归**行为不一致**：1 层能往返，2 层才丢；且丢的是**内层类型的成员**（`Probe_Node.Child`），不是用户看到的那个成员 | S11：yaml 1 层 ✅ / 2 层 ⛔003；json/msgpack 2 层 ✅ | R2（诊断指向的类型与用户直觉不符）+ 一致性 |

> **D-1/D-2 的影响面**：任何用户在 MsgPack/TOML/YAML/INI 里用了 `HashSet<T>` 成员，字段会**无声消失**。这是本轮审计后仍存在的最高危静默丢失。

## 5. 待决事项（需签字）

### D1 — YAML 序列中的 `null` 元素

YAML **本身支持** null（`null` / `~` / 空）。当前不支持是**库的选择**（写侧省略 null 成员），不是格式限制。按 R1，`List<int?>` 在 YAML **应当支持**。

| 选项 | 做法 | 代价 | 兼容性 |
|---|---|---|---|
| **D1-A（建议）** | 支持。写侧新增 `WriteSequenceItemNull()` 发射 `- null`；生成器序列项增加 `IsNullLiteral` 分支；放开 `GenInfrastructure` 对 yaml 的 `leafIsNullableValueType` 判定 | 中：`YamlWriter` + YAML 生成器序列项发射 + 提取期判据；约 3 个 Task | 只影响此后生成的代码；既有数据（无 null 元素）不变 |
| D1-B | 保持不支持（现状） | 0 | 用户无法用 YAML 表达 YAML 能表达的东西 |

> **D1 与 F5 的冲突点**：现有的三态判别是「裸 `-`=嵌套序列项」「`- []`=空嵌套序列」「`- "[]"`=字符串」。`- null` 是**第四态**，不冲突；但**裸 `-` 不能被同时用作 null 元素**，否则会破坏 F5。
>
> **D1b（建议不动）**：写侧「null **成员**省略」改为写 `null`。这会改变既有输出且破坏往返保真约定，建议保持现状。

### D2 — 扩展集合的格式归属

| 选项 | 做法 | 代价 | 兼容性 |
|---|---|---|---|
| **D2-A（建议）** | 全格式支持：去掉 `TypeKindResolver.cs:71` 的 `if (format == "json")` 门槛，各生成器补 `HashSet` 等的读侧构造 | 中：`TypeKindResolver` 一处 + 5 个生成器的容器构造；约 4 个 Task | 原本静默消失的成员**会出现**（行为变更，但是修复） |
| **D2-B** | 仅立刻消除静默：非 JSON 格式报 004，保持 JSON 专属 | 小：提取期加判据；约 1 个 Task | 输出不变，只是从静默变响亮 |

> **建议组合**：**先 B（立即止血，Step 1）**，**再 A（Step 2 能力放开）**。两者不冲突，B 是 A 的前置安全垫。

### D3 — section 格式的递归

| 选项 | 做法 | 代价 | 兼容性 |
|---|---|---|---|
| **D3-A（建议）** | 保持丢弃，但**修 D-4 的不一致**：YAML 从第 0 层就判定，别让 1 层"碰巧能用" | 小 | 已有 YAML 递归用户会失去那 1 层（属于纠正不一致） |
| D3-B | 加运行时深度守卫，支持到固定深度 N | 大：5 个生成器的读循环 + 写入侧 + 文档声明 N | 「无限深」语义变为「N 层」 |

> 理由：TOML/YAML/INI 的 wire 结构是固定层级，无法忠实编码任意深度（R1）；且深度守卫要改的正是 F5/reader 的状态机区域。

## 7. 不变式（必须由测试强制）

| ID | 不变式 | 强制方式 |
|---|---|---|
| **I-1** | 任何未进入生成代码的成员都产生 `PICOSERDE003`/`PICOSERDE004` | 生成器驱动测试：对每个 ⛔ 形状断言诊断 id 出现 |
| **I-2** | 任何 ⛔ 形状**不得**产出不可编译代码 | 每个 ⛔ 形状有一条「能编译」的编译级测试（F5 review I-3 的教训） |
| **I-3** | `FormatCapabilities` 表是**唯一**判据来源；不得再有 `if (formatTag == ...)` 直接决定能力 | 静态测试：`shared/Gen` 中能力类判定只允许出现在 `FormatCapabilities`；测试断言表 ↔ README 矩阵逐格一致 |
| **I-4** | 每个 ✅ 必须有 round-trip 测试，且逐格映射到矩阵行 | 一条矩阵↔测试映射测试（缺一格即失败） |
| **I-5** | 诊断消息含成员名 + 格式 + 形状 | 断言消息片段 |

## 10. 附录：如何复现 §3 矩阵

1. 建一个引用 5 个运行时 + 5 个生成器（`OutputItemType="Analyzer" ReferenceOutputAssembly="true"`）的测试项目。
2. 为每个（格式 × 形状）声明一个 `[Pico*Serializable] partial class {K; V}`。
3. **诊断**：构建时**不要** `NoWarn` `PICOSERDE003/004`，从构建日志收集 `Member '...V'` 条目 → ⛔ 格。
4. **往返**：对每个形状 `Serialize → Deserialize → 断言`，失败即 🐞（若该格无诊断）或 ⚠️（若部分成功）。
5. 探针实现见本轮会话的 `MatrixProbe`（已删除，未入库；重建约 30 分钟）。
