### `IFusedTokenReader` / `TokenReaderFused` 是什么

一句话：把"`Read()` 分类 + `TryGetX()` 解码"这两次分派合成一次的可选能力接口 ——
`ref struct` reader 自己实现（不能做成 `ITokenReader` 的新成员，那会撞 `CS9245` 并破坏所有 out-of-tree
实现者），`TokenReaderFused` 是这些覆写**必须逐字相等**的参考语义。它不给使用者新的调用面，给的是格式
reader 的性能契约；**哪个成员真的被生成器发射、哪个只是实现了但没人调用**，逐条登记在被
`FusedMemberEmissionGuardTests` 强制执行的那张表里：
[`docs/fused-emission-registry.md`](../fused-emission-registry.md)。

## 2. Wire delta：MsgPack 的 `DateTime` 默认编码变了

| | v2026.10.0（旧） | v2026.11.0（新，默认） |
|---|---|---|
| 写出形态 | 28 字符 ISO 8601 文本（`"O"`），msgpack `str` | MessagePack **timestamp extension**，application tag `0xFF` |
| 字节 | 文本 | timestamp 32（`0xD6 0xFF` + 4 字节秒）；timestamp 64（`0xD7 0xFF` + `(nsec << 34) \| sec`）当秒 < 2^34；其余 timestamp 96（`0xC7 0x0C 0xFF` + 4 字节纳秒 + 8 字节有符号秒） |
| 想回到旧形态 | — | `MsgPackOptions.DateTimeFormat = MsgPackDateTimeFormat.IsoString`（默认是 `TimestampExt`） |
| 读旧数据 | — | **照旧可读**：reader 继续接受 28 字符 ISO 文本，已存 payload 不需要重写 |

依据：

- `PicoMsgPack/README.md:96–109`（`### DateTime on the wire` 整节）
- `PicoMsgPack/src/PicoMsgPack/MsgPackWriter.cs:40`（`TimestampExtTag = 0xFF`）、`:577–616`（三种编码 + Kind 政策）、`:617`（`WriteDateTime`）、`:625–626`（`Local` → `ToUniversalTime()`）
- `PicoMsgPack/src/PicoMsgPack/MsgPackOptions.cs:20`（`TimestampExt = 0`）、`:29`（`IsoString = 1`）、`:48`（默认值）
- 测试：`TimestampInteropTests.Default_DateTimeFormat_is_the_timestamp_extension`、`IsoString_option_reproduces_the_legacy_wire`、`Legacy_iso_string_payload_still_deserializes`、`Legacy_iso_string_payload_with_an_offset_still_deserializes`、`Our_timestamp_bytes_are_read_by_MessagePackCSharp_tick_for_tick`、`MessagePackCSharp_timestamp_bytes_are_read_by_us_tick_for_tick`

这是**面向对端的字节变更**：C# 公开面动了（`+15`），但真正重要的是同一条 `DateTime` 现在落在不同的字节形态上。
与 MessagePack-CSharp 逐字节相同，`TimestampInteropTests` 两个方向都逐 tick 断言。

## 3. 语义变更（不是 API 变更，但消费者会感知）：`DateTimeKind` 归一到 `Utc`

timestamp extension 携带的是**瞬时**（秒 + 纳秒），没有字段装 `DateTimeKind`：

| 写出的 `Kind` | 写前怎么处理 | 读回 |
|---|---|---|
| `Utc` | 原样 | `Utc` |
| `Local` | `ToUniversalTime()` | `Utc` |
| `Unspecified` | 按 UTC 理解，ticks 原样上 wire | `Utc` |

结论：一个 `Local` 或 `Unspecified` 值往返一次，值变成 `Utc`；**瞬时不变、ticks 不变**（`Local` 先转 UTC，所以
没有任何时刻在移动；`Unspecified` 的 ticks 直接上 wire）。**这是行为变更，不是破损** —— 同样的字节在
MessagePack-CSharp 里读出同样的 `Kind`，互操作测试逐 tick 断言两个方向。

依据：`api/PENDING-CHANGES.md:66–81`（R-2 的 "Registered capability change" 段；账目清理后这一节的行号变了，内容与语义未变）、
`PicoMsgPack/src/PicoMsgPack/MsgPackWriter.cs:603–609`、`PicoMsgPack/README.md:104–106`、
测试 `TimestampInteropTests.Unspecified_values_are_interpreted_as_Utc`、
`Local_values_are_converted_to_Utc`、`Utc_values_keep_their_ticks`。

**谁会中招**：把 `DateTimeKind` 当业务语义用的消费者（例如靠 `Kind == Local` 决定显示时区）。修法是在 DTO 层自带
时区字段，或者留在 `MsgPackDateTimeFormat.IsoString`（字节与值与 v2026.10.0 一致）。
