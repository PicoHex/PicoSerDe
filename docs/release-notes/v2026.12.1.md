### 1.1 `b22cdec` —— 属性名预留 3 字节，实际写 4

`WritePropertyName(ReadOnlySpan<byte>)` 把 `,`（可选）`"` name `"` `:` 一次性放在一个 `Ensure(n + 3)` 后面，
但带逗号的那条分支写的是 `n + 4` 字节。`Ensure` 只在剩余**少于**申请量时补充，于是"恰好剩 `n + 3`"能过检查、
冒号那次 store 落到缓冲区尾后一字节 —— `IndexOutOfRangeException`（当时在 `JsonWriter.cs:637`）。

修复是一行：`Ensure(n + 3)` → `Ensure(n + 4)`（现 `PicoJetson/src/PicoJetson/JsonWriter.cs:668`）。
同族审计（`WriteFormattable` / `TryWriteShortAsciiString` / `TryWriteLongString` / `WriteRaw` / `WriteByte`）
确认**这是唯一**预留短于实际写入的地方。

触发条件实测（`ea4f514` 上探针遍历 `(跨度形状, n)`）：精确提示跨度 + 两个成员 ⇒ `n = 252..300` 抛；
指针对准该字节 ⇒ `n = 0..245` **全部**抛（最小触发是"0 字节名字 + 剩 3 字节"）。
`new ArrayBufferWriter<byte>()`（`RentWriter` 给的那个）只在 `n = 252`、`260`、`508`、`1020` 一类长度上
暴露，因为它翻倍扩容 —— 所以"扩容把窗口盖住了"只对**测试恰好用到的那种跨度**成立，不是普遍结论。

测试文件 `PicoJetson/tests/PicoJetson.Unit.Tests/JsonWriterPropertyNameReservationTests.cs`（311 行、5 个测试）
在 `ea4f514` 上红、在此提交上绿。

### 1.2 `bfe8251` —— 四种误用过去写出去，现在当场抛

`JsonWriter` 接受 `Utf8JsonWriter` 会拒绝的四次调用，然后**静默**产出一份没有 reader 接受的文档：

| 编号 | 误用 | 过去写出的字节 |
|---|---|---|
| W1 | 对象里没有属性名就写值 | `{"x"}` |
| W2 | 连写两个属性名 | `{"a":,"b":1}` |
| W3 | 多关一次（`depth` 掉到 -1） | 空输出，或把多余的 `}` 吞掉 ⇒ `{"a":1}` 被当成合法 |
| W4 | 对象里写 `]` 收尾 | `{]` |

现在四条都在**写点**抛 `InvalidOperationException`，消息用 `Utf8JsonWriter` 的原文，且**在暂存任何字节之前**
（`W1_Rejection_happens_before_anything_is_written` 钉住这一点）。

实现是每个嵌套层一位的 `_kinds` 位掩码（`PicoJetson/src/PicoJetson/JsonWriter.cs:23`），与既有的
`_needsComma` 同索引方式：第 `_depth` 位为 1 表示这一层是对象 —— 对象开时置位（`:722`）、数组开时清位
（`:749`）、`']'` 收尾时据此判 W4（`:758`）、`ThrowIfValueInObjectWithoutName` 据此判 W1（`:818`）。
W2 是 `WritePropertyName` 开头的一行（`:642`）。因为构造函数把 `maxDepth` 封在 63，最深容器正好是 bit 63，
**一个 `ulong` 够用**，不新增公开面。数字路径自己暂存分隔符，所以它也要问同一个问题，否则 `{1}` 照样会出去。
`BytesWritten` 的 XML 注释现在说清它数的是"已写字节，含仍暂存的"。

**合法调用一个字节都没变**：`tests/FormatCapabilities.Probe/generated-baseline` 96 个文件 sha256 全同，
清单摘要 `4000e80b…` 前后一致。

> 这条提交的作者当时标了 "NOT MERGEABLE AS IS"：新守卫暴露出**生成器**在嵌套匿名对象上一直少写一对
> `{}`（第 1.3 条）。两提交按顺序合并后该问题消失 —— `321dca2` 是这条守卫的配套修复，不是可选的。

### 1.3 `321dca2` —— 嵌套匿名对象缺 `{}`，产出非法 JSON

`shared/Gen/AnonTypeHandler.cs` 的嵌套 helper 只写成员的**内部**，从不写容器。于是

```csharp
new { Outer = "root", Inner = new { X = 1, Y = 2 } }
```

在 `main`（`ea4f514`）上序列化成 `{"Outer":"root","Inner":"X":1,"Y":2}` —— 外层键写完了、暂存的分隔符冲出去了、
内层属性名落进了值的位置。两层嵌套的情况是 `{"A":{"B":{"C":1}}}` → `{"A":,"B":,"C":1}`。

修复：helper 现在发出与顶层拦截器**同一对** `ObjectStartMethod` / `ObjectEndMethod`
（`AnonTypeHandler.cs:995` 的 `EmitNestedSerialize`，对：`:657` / `:688`）。计数只在 writer 需要计数时给
—— MessagePack 的 `WriteStartObject(int)` 拿 `EmittedFieldCount(info)`（与外壳头同一个"实际写出几个成员"的
答案），JSON / YAML 不带计数。INI 与 TOML 根本没有这一对（它们的嵌套内容是 `WriteSection` / `WriteTable`
的名字），所以它们的生成代码**一个字节未变**。

测试从"三个子串"改成**整份文档**：那三个子串在缺括号的输出上**都成立**，这正是缺陷能在绿灯下活下来的原因。
每个 JSON 用例现在加 `PicoDocument.IsValid` 加一次 DOM 读取（匿名类型没有 setter，回程是 DOM 而不是反序列化）。
新增 5 个用例：两层嵌套、嵌套对象里有集合、嵌套对象里有 null 成员、嵌套对象**自身**为 null（改前改后都绿 ——
它不该被加上括号）、YAML 的缩进。

### 1.4 `3c83308` —— `PicoDocument.IsValid` 把缺逗号判成合法

`IsValid` 曾把 `{"a":1"b":2}` 与 `[1 2]` 报成**合法** JSON。它是本仓库（以及下游）回答"这份输出对不对"的
那把尺子，所以这里的假阳性比 writer 写错更糟：**它给错的字节盖章**。

成因在 `JsonStructureValidator`（`PicoJetson/src/PicoJetson/PicoDocument.cs`）：对象侧一个值消费完后状态停在
"期望属性名或结束"，而属性名只要求那个状态，于是下一个名字不用逗号也收；数组侧那句注释
（"arrays keep expecting value-or-end"）本身就是 bug —— 状态从不离开 0，`[1 2]` 看起来像新元素，**已关闭的
容器**看起来像什么都没消费（`[{"a":1}2]` 也曾判合法）。

修复是同一状态机的**最小扩展**，不是重写：新增第四个期望 `ExpectSeparatorOrEnd`（`:497`），值完成（标量，
或容器关闭）时进入、只由结束括号或逗号离开。因为 reader 吞掉 `,` 时不发 token，validator 从它拿到的**原始
字节间隙**里解析这一个转移（`HasComma`，`:589`；每个间隙最多一个逗号，前置/重复/尾随逗号本来就是 reader 的事）。

证据：先红（15 个新测试里 9 个在 `64780b7` 上红，而已有 74 个 `PicoDocument*` 测试在同一个提交上全绿 ⇒
新文件是**为它自己的原因**红的）；对 `System.Text.Json`（RFC 8259 的 oracle）与一份逐字复刻的修复前 validator
做 44,000 份文档的差分 fuzz —— **0 处收紧**（oracle 认为合法的没有被新判非法）、**0 处放宽**（旧 validator
拒的没有被新接受）、**1,300** 个判定从假阳性翻成正确。剩下 50 个"接受但非法"的用例全是**字符串里的裸控制
字符**，属 reader 的宽容度，本次不动。

**代价（本版唯一一条性能变化）**：Release、同进程、位置均衡 ABBA、100k 次、1KB 与 100KB 的 compact + pretty ——
**+2.8 % … +6.0 % ns/call**（对照组的同代码重测是 -2.0 % … +2.2 %，所以成本是真的，且低于 10 % 线）。
**每调用零分配增量**；既有的 560 B/call（validator 的两个 `byte[maxDepth]` 数组）不变。

### 1.5 `95990ee` —— 零成员类型不再整个消失

`[PicoSerializable] public sealed class CapabilityMark { }` 作为成员时，**整个成员**曾消失：
`TypeKindResolver.Resolve` 的"嵌套复杂类型"分支只在类型声明了带 getter 的公开实例属性或公开实例字段时才答
"object"，两样都没有就落到 `(null, …)`（"当前格式无法解析"），提取阶段带着 PICOSERDE001 ⏸ 把成员丢掉。
于是文档读作 `{"SessionCapabilities":{}}`，而模型写的是 `{"SessionCapabilities":{"List":{}}}`。⏸ 本身
就是这个缺陷的自供：**格式放得下，是我们没实现**。

现在这条分支是一个 **EMPTY-OBJECT 形状**（`shared/Gen/TypeKindResolver.cs:368` 的 `EmptyObjectBlockOf`，
五个闸门逐一堵住 `{}` 会变成谎言的路径）：格式必须真有这个形式（问能力模型，不假设）；类型必须可实例化；
必须有无参构造；基类不得把成员带进来（`Opaque : Exception` 拿 `{}` 就是静默丢数据，而丢成员的旧行为是响的）。
"零成员"比"循环一个成员都没接受"更窄 —— 只有 getter 的属性是我们**拒绝序列化**的成员，所以
`KeyValuePair<,>` / `Tuple<,>` 保持今天这个响亮的丢弃，而不是悄悄变成 `{}`（这条边界是 PicoJetson 那对
fixture 抓出来的）。

四种格式各有自己的语法，缺分支的两个补上了：

| 格式 | 空对象写成 | 说明 |
|---|---|---|
| JSON | `{}` | 发射器本来就会写 |
| MsgPack | 空 map | 过去写的是 NULL |
| TOML | `[Mark]` / `[[Marks]]` | 空表头，用 tomllib 量过 |
| INI | `[Mark]` | 没有键的 section |
| **YAML** | **仍然丢（⏸ 已登记欠账）** | `YamlWriter` 没有空映射形式，补它要改运行时（`api/PicoYaml.public.txt` 会跟着动） |

### 1.6 `6e36987` —— 三个"永远做不到"的边界从 ⏸ 改成 ⛔

`95990ee` 把三个边界保留为丢弃：`abstract`、`static class`、只有带参构造的类型。这用的是 `main` 上**既有的**
⏸ 措辞（`95990ee` 只是把这三个边界写进了代码与测试）："json 格式能表达这个形状，但本生成器还没实现，
这是一个已记录的缺口 … reopen …"。**三个都永远实现不了**：
生成的 reader 需要 `new T()`，C# 在每种格式上都拒绝（`CS0144` / `CS0712` / `CS7036`），所以那条消息承诺了一个
不可能发生的 reopen —— 这正是 AGENTS.md 规则 3 的另一半："把事实叫成欠账也是错的"。

改法：空对象分支的五道闸门搬进 `TypeKindResolver.EmptyObjectBlockOf`，**丢弃点向同一段代码要判决** ——
三道是终局（`DropVerdict.TypeUnconstructible` ⇒ ⛔），两道仍可 reopen（我们的 writer 没有空形式 ⇒ yaml；
基类仍带成员 ⇒ ⏸），所以判决不可能背离产生它的那个决定。新 PICOSERDE001 模板**终局且诚实**：说格式放得下、
类型放不下，既不说"json 格式表达不了"（假的，`{}` 就是 JSON），也不说"换个能表达的格式"（五路都是死路）。

同一提交里还有两个附带的收紧：`internal` 无参构造只在**正在生成的那个编译单元内声明**的类型上被接受
（从元数据来的类型调用不了 internal 构造，`CS1729`，那半边继续 ⛔，用双程序集 in-memory fixture 钉住）；
TOML 的 `IsEmptyObjectShape` 判的是"提取阶段看见成员了吗"而非"类型声明了零成员吗" —— 两个反例实测下来
前者才是正确的那条分支，理由写在它旁边并用测试钉住。

## 2. 消费者可见的语义变化 —— `api/*.public.txt` 看不见

**这两条不在 `api/` 里，升级前请确认你的 token 消费逻辑。**

`api/` 比的是**签名**。下面两条只动**同一个方法返回的 token 序列**：方法名没变、参数没变、返回类型没变、
枚举没变 —— `-DryRun` 报 `API changed: false` 完全正确，而下游按 token 流走的代码会读到不一样的形状。

| # | 变化 | commit | 影响 |
|---|---|---|---|
| **S1** | YAML token 流不再多吐一个尾部 `ObjectEnd` | `1b5f92f` | 嵌套文档过去读到 `Depth == -1`；**依赖"多一个 ObjectEnd"兜底的消费方要删掉那段补偿** |
| **S2** | YAML 块/flow 序列改发 `ArrayStart`/`ArrayEnd` | `2b0552e` | 过去序列与映射都用 `ObjectStart` ⇒ 只能靠"后面跟什么"猜；**两个相邻序列会丢键** |
| **S3** | 零成员对象形状（第 1.5 条） | `95990ee` + `6e36987` | YAML 仍丢（⏸），JSON/MsgPack/TOML/INI 写出空对象 |

**旧形状 → 新形状，一行对照**（S1、S2 各一行，S3 一行）：

| 项 | 旧形状（`v2026.12.0`） | 新形状（`v2026.12.1`） |
|---|---|---|
| S1 嵌套映射的收尾 | `A:\n  B: 1` ⇒ `PropertyName(A) ObjectStart PropertyName(B) ObjectEnd ObjectEnd` —— **两个 `ObjectEnd` 对一个 `ObjectStart`**，opens=1、closes=2，走完 `Depth == -1` | `PropertyName(A) ObjectStart PropertyName(B) ObjectEnd` —— opens==closes，走完 `Depth == 0` |
| S2 序列的容器种类 | `A:\n  - 1\n  - 2` ⇒ `PropertyName(A) ObjectStart String(1) String(2) ObjectEnd`（与映射**同一对**） | `PropertyName(A) ArrayStart String(1) String(2) ArrayEnd`（映射仍是 `ObjectStart/ObjectEnd`） |
| S3 零成员成员 | 成员**整个消失**：模型说 `{"Capabilities":{"List":{}}}`，写过 `{"Capabilities":{}}`；YAML 同样丢 | JSON `{"Capabilities":{"List":{}}}`；MsgPack 空 map；TOML `[Mark]`；INI `[Mark]`；**YAML 仍然丢** |

### 2.1 S1：一个容器一个缩进帧，嵌套文档在 `Depth == 0` 结束

reader 对缩进文档的**第一次打开**压了**两帧**（一个 level-0 哨兵 + 真实层）却只发一个 `ObjectStart`，而 pop
侧是**一帧一个 `ObjectEnd`**。哨兵因此制造了一个没人打开过的收尾 token：`A:\n  B: 1` 产出 opens=1 / closes=2、
走完停在 `Depth == -1`，而且**下游真在量它**（`PicoCfg.YamlFlattener` 里就有一句"reader 会在最后一个 close 之后
多吐一个 `ObjectEnd`"的守卫）。

规则改回"一帧 = 一个容器，不是缩进书签"：push == open，pop == close（注释与 `PushIndent` 见
`PicoYaml/src/PicoYaml/YamlReader.cs:2390-2397`）。四个 push 点（span + sequence 模式 × 根块 + 文档起点）
都只压真实那一层，pop 侧与每一个合法 token 都**没变** —— 32 份文档过两种 reader 形状的普查显示唯一差异就是这个
`Depth == -1` 上的尾部 `ObjectEnd` 消失（PropertyName / String / flow / anchor / block-scalar 流逐字节相同）。

**你要删的东西**：任何形如"YAML reader 会多给一个 `ObjectEnd`，所以要跳过/忽略最后一个"的补偿分支。
留着它现在会**吃掉一个真实的收尾**，症状是最后一个容器的关闭被漏掉、`Depth` 少减一次。

落点：`tests/PicoSerDe.Integration.Tests/TokenReaderConformanceTests.cs:56` 的
`Yaml_NestedDocument_ClosesEveryContainerItOpens`（5 种形状 × span/sequence），`65e31c0` 上红
（opens 2 != closes 3，end Depth -1）。注意这个不变量（opens == closes、end Depth == 0）此前**从没在嵌套
输入上断言过** —— 一致性测试只覆盖了 `a: 1`，一份连容器 token 都没有的文档。

### 2.2 S2：序列的容器 token 是 array，不是 object

块序列（以及 flow 序列）过去发 `ObjectStart/ObjectEnd` —— 与映射**完全相同**的一对 —— 所以没有消费方能从
token 本身分辨两种形状，只能靠"后面跟什么"去猜。这不是抽象抱怨：下游一个 flattener 在两个**相邻**的序列值上
丢了 `B` 这个键（`B[0]` 变成 `0:0`），因为第二个 `ObjectStart` 与第一个无法区分。

现在：序列开 `ArrayStart`/`ArrayEnd`，映射保持 `ObjectStart`/`ObjectEnd`，**按容器类型区分**。
序列**元素**仍然是"每行一个 String token"（裸 dash 仍保留 `IsNestedSequenceItem`），所以生成式 reader
的元素形状没变。

实现：每帧记住自己的种类（`PushIndent(i, isSeq)` 在 `YamlReader.cs:2397`，`PopIndent()` 返回该种类自己的
收尾 token，帧种类的数组是 `_frameIsSeq`，`:52`），四条关闭路径都报这个种类；**没有缩进包装**的序列（文档根，或 dash 与键同列的序列）现在也拿到自己的
`ArrayStart..ArrayEnd` 对 —— 改前它**一个容器 token 都没有**，正是这一点把消费者逼成靠 String token 猜。
flow 序列同规则（含 `[1,2,3]` 与 `[]`），flow 映射与 flow 路径的 `Depth` 行为不动（见 3.2）。
`YamlReaderState` 带上帧种类，所以按 chunk 重建的流式 reader 也记得（逐字节回环验证过）。
生成器的 8 个序列包装探针（4 个发射器）跟着改，所以**生成式序列化器的行为不变**。

**你要改的东西**：把"序列 ⇒ 看 `ObjectStart`"的判定换成按 token 种类分流；再检查一遍"两个相邻序列"的分支
—— 它过去靠键序与 `ObjectStart` 的配对猜，现在有了明确的 `ArrayStart/ArrayEnd`。

落点：`PicoYaml/tests/PicoYaml.Tests/YamlSequenceTokenKindTests.cs`（346 行）——
`TwoAdjacentSequenceValues_KeepBothKeys_EachWithItsOwnArray` 正是下游 `0:0` 那个症状的复现，
`FlowSequence_IsArrayDelimited` / `FlowMapping_StaysAnObject` / `TopLevelBlockSequence_IsArrayDelimited` /
`GenericConsumer_KeepsBothKeys_WhenTheDistinctionIsOnTheWire`（一个**通用**消费方，不认格式）各钉一面；
平衡侧 `EveryContainerCloses_AndEndsAtDepthZero`。回环侧 `YamlSequenceRoundTripTests` 6 个用例
（含 `StreamingRoundTrip_OneByteChunks_KeepsTheSiblingKey`、`HandWrittenWires_StillRead`）。

生成代码基线 96 个文件里 **11 个变化 —— 全部是 YAML**，每处改动行都是四种包装形式之一（探针 / 收尾 /
嵌套块探针 / 两处注释）。也就是说：**生成的序列化器照旧可读回自己的输出**，变的是 reader 给的 token 种类。

### 2.3 S3：零成员形状（第 1.5 条的消费方视角）

同一个模型现在在四个格式上有输出、在 YAML 上仍然消失。如果下游有"成员不存在 ⇒ 用默认值"的分支，
JSON/MsgPack/TOML/INI 上它会**第一次真的拿到**一个空对象；YAML 上行为与 `v2026.12.0` 完全一致。
YAML 的空映射是登记在案的 ⏸ 欠账（`DecisionTables.EmptyObjectFormats` 就写着 yaml 缺这一项），不是格式限制。

## 3. 不说的（诚实边界）

### 3.1 YAML 内联成员融合 —— **⏸ 欠账（我们 tokenizer 的融合，不是 YAML 的要求）**；拆开属于契约变更（x 轴），所以只能等 x 轴

序列项里**第一个内联成员**是融合成一个 String token 交付的，不是 `PropertyName` + 值。实测（`main` 上探针）：

```
Items:
  - name: x
    port: 1
```

```
PropertyName depth=0 key="Items"
ArrayStart   depth=1 key="Items"
String       depth=1 key="Items" value="name: x"    ← 融合成一个 token
ObjectStart  depth=2 key="Items"
PropertyName depth=2 key="port" value="1"
ObjectEnd    depth=1
ArrayEnd     depth=0
end Depth=0
```

`- name: x` 单独成项时**连 `ObjectStart` 都没有**（只有 `ArrayStart` → `String` → `ArrayEnd`）。

**这是我们的 tokenizer 取巧，不是 YAML 的要求 —— ⏸ 欠账，可以 reopen**。在 YAML 里 `- name: x` 这一项
**本来就是一个 block mapping**（dash 只是序列项指示符，`name: x` 是该项的 mapping 内容）：键 `name`、值 `x`。
**符合语法的 token 流应当发** `ObjectStart` + `PropertyName("name")` + `String("x")`，收尾配 `ObjectEnd`。
我们发的是一个**裸标量** `String("name: x")` —— 因为在 `PicoYaml/src/PicoYaml/YamlReader.cs:1069-1079` 里，
序列项的值是"**该行余下的文本**"整段抓成标量的（`itemText = _data[vs.._position]`，一直扫到行尾），
dash 后面跟着什么就整段当值。所以这个形状是**我们融合出来的** —— "就是这样"只能用于"格式标准本来
就是如此"，不能用于"我们暂时实现成这样"。

**为什么本版仍然不修 —— 而这恰恰说明它只能留作欠账、等 x 轴**：要拆开就得让"同一行里既是键又是值"的结构
发出 `ObjectStart` + `PropertyName` + 值，那是**契约变更（x 轴）**，y 轴的修复做不了。但"属于 x 轴"是**排期
结论，不是定性结论**：`ITokenReader` 的契约（`PicoSerDe.Core/src/ITokenReader.cs`）只承诺 `Read` /
`TokenType` / `Depth` / `TryGet*` 这一组，**没有把 token 形状钉死** —— 契约沉默只说明"契约没管到这一层"，
不说明"这一层我们做对了"。AGENTS.md 规则 2 管的正是这种情形：⏸ 是**我们的**欠账、可 reopen、**不许赖格式**；
规则 3 的另一半同样不允许把**我们自己没做的那一步**说成格式的形状。reopen 条件写在这里：tokenizer 不再把
行尾整段当标量、改发 `ObjectStart` + `PropertyName` + 值 ⇒ 那一刻按 **x 轴**处理（`api/` 一行未动 **≠**
不是契约变更 —— 卷首 ⚠ 说的就是这件事），本节与 [`PicoYaml/README.md`](../../PicoYaml/README.md) 的
"Known shapes a consumer must handle" 一起改。**这一项也没有机读登记位**
（`DecisionTables.EmptyObjectFormats` 管的是生成能力，不是 reader 的 token 形状）—— **本条就是它的登记**。

**生成式序列化器不受影响**：`YamlWriter.WriteStartSequenceBlock`
（`PicoYaml/src/PicoYaml/YamlWriter.cs:446`）写的是**独立的 dash 行**，内容在它下面的缩进里 ——
"The dash stands alone: no trailing space" —— 因此生成器的输出永远不会落到"内联成员"这个形状上，
`YamlSequenceRoundTripTests` 的 6 个回环用例（含 `StreamingRoundTrip_OneByteChunks_KeepsTheSiblingKey`）
在 `2b0552e` 前后都绿。

### 3.2 flow 集合的 `_depth` 记账 —— **仍是空缺，本版未变**

`A: [1,2]` 这类 flow 集合不发深度变化（实测 `ArrayStart depth=0` → 两个元素 `depth=0` → `ArrayEnd depth=0`，
而块序列的 `ArrayStart` 是 `depth=1`）。这是一个既存的**记账空缺**，`2b0552e` 的消息里写明"flow sequences
follow the same rule；flow mappings and the flow path's Depth behaviour are untouched"。也就是说：
**flow 路径的 `Depth` 数值与 `v2026.12.0` 一致**，`2b0552e` 只改了种类、没动深度。要是你的消费方按 `Depth`
判断 flow 集合的嵌套，本版**不会**让它变好，也不会让它变坏 —— 但反过来说，S1 的平衡保证（opens == closes、
走完 `Depth == 0`）在 flow 上**同样成立**，因为 flow 集合本就不动 `Depth`。

### 3.3 跨包：本版没有 `v2026.12.0` 第 5 节那个问题

本版 `api/` 一行未动 ⇒ **不存在**"按旧公开面编译的二进制在运行期 `MissingMethodException`"的场景，兄弟包
（`PicoJsonRpc` 等）不需要因为本版重发。那一节的结构性结论（开区间下界挡不住签名不兼容，只能靠重发把下界
抬起来）仍然适用于以后每一次删类型 / 改签名 —— **不重复抄写，见
[`v2026.12.0.md` 第 5 节](v2026.12.0.md#5-跨包兼容同时引用兄弟包的消费者不是-drop-in)**。

需要区分的是两个**非二进制**的方向：(a) 本版 S1/S2 影响的是**源码级**的 token 消费逻辑（第 2 节），
重新编译就能暴露，最坏是逻辑错而不是 `MissingMethodException`；(b) `PicoCfg` 那类下游必须按 S1 删掉补偿
逻辑 —— 那是源码改动，不是重发版本约束。

## 4. 升级检查清单

1. **搜一遍 YAML 的 token 补偿**：`grep -rn "trailing ObjectEnd\|多一个 ObjectEnd\|Depth == -1\|Depth < 0" <你的代码>`。
   有命中就是 S1 的受害者 —— 删掉那段补偿（第 2.1 节）。
