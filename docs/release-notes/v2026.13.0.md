## 0. 一句话 —— 本版是什么

**这是新增 API 的 x 版本，不是破坏性版本**：`+10 / -0`，全在 `PicoJetson`，**没有删除任何类型或成员、没有改任何签名**；
十行里九行是 `JsonWriter` 上的新成员，第十行是它实现 `System.IDisposable`。

本版修的不是"某个 helper 写错了"，而是**为什么每个下游作者都会把 helper 写错**。一条成员今天要两次调用
（`WritePropertyName(name)` 然后 `WriteX(value)`），而这两次调用之间可以出错、出错时**什么都不抛**；
本版把那一对合并成**一次不可能被拆开的调用**（`Write*Property`），并让"我写完了"第一次可以被说出来
（`Flush()` / `Dispose()`）。**既有写法一个字节都没变，仍然完全可用。**

| 类 | 条数 | 公开面 | 消费者要做什么 |
|---|--:|---|---|
| **新增** `Write*Property(name, value)` ×7 | 7 行 | **+7** | 想根治 helper 一类 bug 就改用它；不改也不会坏 |
| **新增** `Flush()` / `Dispose()` / `IDisposable` | 3 行 | **+3** | 想让"异常路径也提交"成立就写 `using var w = new JsonWriter(buf);` |
| **bug 修复** `WriteEndObject` 容器种类守卫 | 0 行 | **不变** | 只有**误用**会被抛（`[}` 过去静默产出），合法调用零变化 |

**本版没有**：删类型 / 改签名 / 改枚举数值 / 改既有合法调用的线上字节。`v2026.12.0` 那种"按旧公开面编译的二进制
在运行期 `MissingMethodException`"的问题本版**不会**产生（`-0` ⇒ 无删除，交叉引用见
[`v2026.12.0.md` 第 5 节](v2026.12.0.md#5-跨包兼容同时引用兄弟包的消费者不是-drop-in) 说明该结构何时适用）。

## 1. 为什么是 x 而不是 y

版本规则写在 `scripts/release.ps1` 的注释里，原文两行：

```
x bumps when the public API changed (y resets to 0)
y bumps when it did not
```

**判据是"公开面变没变"，不是"谁会被打断"。** 工具比的是新导出的公开面与 `api/*.public.txt` 这份
"**上一次发布**的表面"之间的差集，`+N / -0` 也是 changed —— 加一行公开面，读者看到的就是一个更大的 API，
所以它走 x，`y` 归 0。本版实测：

```
   PicoJetson: API changed (+10 / -0)
   ...

```

同一把尺子的另一半就是上一个版本：`v2026.12.1` 的 11 个包**一行未动**，因此 `API changed: false` ⇒ `y + 1`。
两个版本合起来才是这条规则的全貌 —— **y 是"公开面没变"，x 是"变了"，不含贬义**；
"破坏性"与"纯新增"的区分写在正文（第 0 节的表），不在版本号里。

## 2. 本版解决的成因（两条，各自一段）

### 2.1 成因一：「名字 + 值」无法一次写完 ⇒ helper 必须 `ref` ⇒ 传错静默丢字节

写一个成员过去（今天也仍然可以）是**两次调用**：

```csharp
w.WritePropertyName("name"u8);
w.WriteString(value);
```

两次调用之间就是错误的容身处，而每个下游作者都会走到同一个地方：既然每次都要写两行，就写一个 helper 把它包起来。
**这个 helper 必须取 `ref JsonWriter`** —— span 游标是 `JsonWriter` 的一个**值字段**，按值传参是复制，复制写进同一段
内存、但它自己的提交永远不会跑，于是那段字节**静默消失**：`JsonWriterSpanCacheTests.PassingTheWriterByValueLosesTheValueWrittenThroughTheCopy`
钉住按值传参输出 `[]`，而欠的是 `[42]`，**不抛**；全仓静态闸 `JsonWriterSpanCacheTests.NoSourceFilePassesTheWriterByValue`
扫过每一个 `.cs` 文件，禁止任何地方按值取 `JsonWriter`。

代价不是"理论上可能"，是**两代下游各自的实测**（`3cd666f` 的消息，与 `PicoJetson/src/PicoJetson/JsonWriter.cs`
里那段同名注释的原文）：**2026.10 丢的是分隔符，2026.11+ 丢的是整个成员**，**两代都不抛**。错误唯一能住的
地方就是 helper 的签名，而签名不会报错。

所以根绝方式不是"再写一份更小心的 helper"，是**把那一对从调用方手里拿走**：一个调用不可能被拆开，
也就没有地方放这个错。

### 2.2 成因二：「我写完了」无法表达 ⇒ `Flush()` private、唯一提交点是 `End*`、没有 `Dispose` ⇒ 早退丢尾部

`Flush()` 过去是 **private**，`JsonWriter` 上唯一说得出"交出去"的调用是最外层的 `WriteEndObject` /
`WriteEndArray`（`depth` 回 0 的那一刻）。`Dispose` 没有，`Complete` 没有，`using` 也就写不出来
（`ref struct` 曾经连作用域钩子都没有）。于是每一次从容器里的提前 `return`、每一个从容器里抛出的异常，
都把尾巴留在 span cache 里：小文档只剩 `{`（1 字节），40 个成员的大文档停在最后一次 256 B 刷新
（`PicoJetson/README.md` → "### Closing a container is the commit point" 实测 **502 B**，收尾是 `,"prop":`），
**不抛**，`PicoDocument.IsValid` 报 `false`。

本版让这句话第一次说得出，两个成员各答一半，**都不关容器、都不抛**：

- `Flush()` —— "**把我写到此为止的交出去**"，容器保持打开，字节仍是文档的合法前缀，调用方可以接着写；
- `Dispose()` —— 同一个提交，加上作用域钩子，于是 `using var w = new JsonWriter(buf);` 在**正常路径、
  提前 `return`、异常展开**三条路上都提交。

**`Dispose()` 不抛是设计上的必要条件，不是宽容**：它会在一场已经在展开的异常里运行，一个会抛的 `Dispose`
会把它存在的那条路打断；而一个会"补一个 `}`"的 `Dispose` 要么产出非法的 `{"a":}`（属性名挂着还没值），
要么对"我还没写完"的调用方撒谎。所以 `using` 是安全的：**它不会因为容器没闭合而抛**，你拿到的是自己写的那些
字节 —— 闭合了就是一份合法文档，没闭合就是一份诚实的半成品。

### 3.1 语义，一句一条

| 成员 | 语义 |
|---|---|
| `void Flush()` | 把 span cache 里挂起的字节提交给 `IBufferWriter`。**不关容器**（不发明括号、不动 `depth`），**从不抛**。之后 `BytesWritten == buffer.WrittenCount` |
| `void Dispose()` / `IDisposable` | 与 `Flush()` 同一个提交，加一个作用域钩子。**提交、不关容器、从不抛**；幂等，且**不结束 writer 的命**（只清 span cache，之后再写会重新取 span 继续） |
| `WriteNullProperty(ROS<byte> name)` | 写 `"name":null`，一次调用 |
| `WriteBooleanProperty(ROS<byte> name, bool)` | 写 `"name":true\|false` |
| `WriteNumberProperty(ROS<byte> name, int)` / `(…, long)` / `(…, double)` | 写 `"name":<数字>`，走既有的 `WriteNumber` 兄弟 ⇒ invariant 格式化、`NumberHandling`（NaN / ±Infinity 与 Strict 下的异常）都是兄弟的，不是第二份实现 |
| `WriteStringProperty(ROS<byte> name, ROS<byte> utf8Value)` | 写 `"name":"value"`，值已预编码为 UTF-8 |
| `WriteStringProperty(ROS<byte> name, ROS<char> value)` | 同上，值给 UTF-16 文本 |

**整族的合同是两条**（`JsonWriterPropertyHelperTests` 逐条钉）：

1. **字节同一**：每一处合法使用，输出与 `WritePropertyName` + `WriteX` **逐字节相同** —— 分隔符、转义、缩进、
   数字格式、失败行为都是（它**委托**给兄弟，不重新暂存字节）。压缩与缩进两种形态都测，10 种形状，
   外加 de-DE 下的文化不变性与 300 字符（超过栈缓冲）的载荷。
2. **必须有一个对象**：根位置、或数组元素位置，`"a":` 根本不是 JSON，所以这七个成员**在任何字节入栈前**
   就抛 `InvalidOperationException`，而两调用形式过去会把裸成员**静默**写出去。这是整族**唯一**的收窄，
   也是"成员形状的入口"该有的样子。

**故意没有的**（不是遗漏，是判定）：`float` 没有孪生重载 —— 它会宽化进 `double` 重载，把 `0.1` 打成
`0.10000000149011612`，一个**安静的数字变化**恰是本版要消灭的那一类失败；`decimal` / `Guid` / `DateTime`
与其余数值种类是同一个理由的弱化版（只影响面、不错字节），暂不加。拿着这些类型的调用方继续用两调用形式，仍完全可用。

## 4. 迁移

**1）旧写法仍完全可用 —— 什么都不用做。** 本版是纯新增（`-0`），`WritePropertyName` + `WriteX`、
`try/finally` + 显式闭合、你自己那个 `ref JsonWriter` 的 helper，全部照旧编译、照旧跑出同样的字节。

**2）想更安全：把 `try/finally` 换成 `using`。** 两种写法今天都对，区别只在**异常路径**：

```csharp
// 过去唯一的写法：早退/异常都要靠 finally 记得闭合
var w = new JsonWriter(buf);
w.WriteStartObject();
try { /* ... 可能在容器中间 return 或抛 ... */ }
finally { w.WriteEndObject(); }     // 这一行就是提交点

// 本版：作用域结束就提交，三条路（正常 / return / 异常）都算
using var w2 = new JsonWriter(buf);
w2.WriteStartObject();
/* ... */
```

注意 `using` **不等于**"自动补 `}`"：它提交，不闭合。`Dispose` 时容器还开着，你得到的是那段诚实的前缀
（`{"a":1` 而不是 `{"a":1}`）—— 想让文档合法，仍然要自己 `WriteEndObject()`，只是不必再把它塞进 `finally`。

**3）自定义 helper 可以删掉，改用 `Write*Property`。** 这是本版的正题，不是风格建议：

```csharp
// 删掉：一对调用 + 一个必须 ref 的 helper = 出错时静默丢字节
static void Prop(ref JsonWriter w, string name, string v) { w.WritePropertyName(…); w.WriteString(v); }

// 换成：一次调用，拆不开
w.WriteStringProperty("name"u8, value);
w.WriteNumberProperty("count"u8, 42);
```

**如果你保留自己的 helper，签名必须是 `ref JsonWriter`**（`in` / `out` 也不行，按值更不行）。这条不是本版的
新要求 —— `JsonWriterSpanCacheTests.NoSourceFilePassesTheWriterByValue` 一直在守它 —— 但本版是第一次让
"不写 helper"成为一个可行的选择。

**4）误用会抛（唯一的行为变化）。** `WriteStartArray()` 之后 `WriteEndObject()` 过去静默产出 `[}`，现在抛
`InvalidOperationException`（第 6 节第 1 条）。跑到就改调用顺序，**别 `catch` 掉** —— 它说的是你的括号记账
已经错了，而过去那份非法文档要等到下游才发现。

## 5. 已知边界 —— 这是设计决定，**不是遗漏**

十行 delta 全在 `PicoJetson` 上，这是**逐 writer 对照过的结论**（`793990f` / `32d3808` 两个提交各带一张
五个 writer 的对照表），不是"只做了 JSON"的省略：

| writer | 有挂起字节吗 | 一次写完名字+值的入口 | 作用域钩子 | 本版 |
|---|---|---|---|---|
| `JsonWriter` | **有**（私有 span cache） | 没有 → **本版加了 `Write*Property`** | 没有 → **本版加了 `Dispose`** | ✅ 全部 |
| `MsgPackWriter` | **有**（`_spanPos` + 私有 `Flush` + `internal FlushToBuffer`） | `WritePropertyName` + 值；`WriteStartObject(count)` 先定 map 长度 | 没有（`FlushToBuffer` 是 internal） | ⏸ **欠**一条公开 `Flush`/`Dispose`，第二阶段 |
| `TomlWriter` | 没有（逐 token 直写 buffer） | **已有** `WriteKeyValue(name, value)` | 不需要（没有挂起字节） | — |
| `IniWriter` | 没有（逐 token 直写 buffer） | **已有** `WriteKeyValue(name, value)` | 不需要 | — |
| `YamlWriter` | 没有（逐 token 直写 buffer） | `WritePropertyName` + 值（两调用） | 不需要 | ⏸ 命名族属第二阶段 |

读法，三条：

- **`Flush()` / `Dispose()` 只加在"真的会挂起字节"的 writer 上。** TOML / INI / YAML 三个 writer 每写一个 token
  就直接落进 `IBufferWriter`，**没有可提交的状态**；给它们一个 `Dispose` 会是在描述它们并不持有的状态 ——
  那和本版要修的病是同一个病（说了一件不成立的事）。**MsgPack 不是这一类**：它有 span cache、有私有 `Flush`、
  有 internal `FlushToBuffer`，所以它**确实欠**一条公开的 `Flush`/`Dispose`，本版**没给**，记在第二阶段，
  不假装它不需要（第 8 节第 4 项）。
- **TOML / INI 不加 `Write*Property`，两个理由各自都成立。** 其一，它们的一次调用入口已经是
  `WriteKeyValue(name, value)`，本版要消灭的那个"两次调用之间"从来没有存在过；其二，它们在**语义上**不是
  property —— 嵌套是 `[table]`（`TomlWriter.WriteTable`）/ `[section]`（`IniWriter.WriteSection`）的**头**，
  不是一个名字后面跟值。把一个 key/value 叫成 `property`，是在用一个别的格式的形状描述它们 —— 撒谎。
- **YAML 有"名字 + 值"的两次调用，但没有挂起字节**，所以它欠的是**命名族**（`Write*Property` 的对应物），
  不欠作用域钩子。属第二阶段。

这三条都写在提交里，不是事后补的解释：`571e1b5` 的消息结句是 "This commit closes the JSON hole; the same audit
for the other four is not claimed."
