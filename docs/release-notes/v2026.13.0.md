## 0. 一句话 —— 本版是什么

**这是新增 API 的 x 版本，不是破坏性版本**：`+20 / -0`，分布在**三个** writer 上，**没有删除任何类型或成员、没有改任何签名**；
二十行里十七行是三个 writer 上的新成员，剩下三行是它们各自实现 `System.IDisposable`（JSON、MsgPack 各一行）。
下面这张表就是 delta 的全部，没有第四行：

| 包（格式） | 新增 | 公开面 | 消费者要做什么 |
|---|---|--:|---|
| `PicoJetson`（JSON） | `Write*Property(name, value)` ×7 + `Flush()` / `Dispose()` / `IDisposable` | **+10** | 想根治 helper 一类 bug、想让"异常路径也提交"成立，就改用它；不改也不会坏 |
| `PicoMsgPack`（MessagePack） | `Flush()` / `Dispose()` / `IDisposable` | **+3** | 想把裸值 / 早退 / 异常里的尾巴交出去，就 `mw.Flush();` 或 `using var mw = new MsgPackWriter(buf);`（过去只能 `_ = mw.Buffer;` 靠 getter 的副作用） |
| `PicoYaml`（YAML） | `Write*Property(name, value)` ×7 | **+7** | 同上，换掉自己那个 `ref YamlWriter` 的 helper |
| bug 修复：`WriteEndObject` 的容器种类守卫（JSON） | — | **0 行** | 只有**误用**会被抛（`[}` 过去静默产出），合法调用零变化 |

**本版没有**：删类型 / 改签名 / 改枚举数值 / 改既有合法调用的线上字节。`v2026.12.0` 那种"按旧公开面编译的二进制
在运行期 `MissingMethodException`"的问题本版**不会**产生（`-0` ⇒ 无删除，交叉引用见
[`v2026.12.0.md` 第 5 节](v2026.12.0.md#5-跨包兼容同时引用兄弟包的消费者不是-drop-in) 说明该结构何时适用）。

**"三个包"是三个 writer 各自的判定，不是"顺手补齐"**：谁拿到哪一半（`Flush`/`Dispose` 还是 `Write*Property`，
或者两样都没有）在第 5 节逐 writer 对照过，那是设计决定，**不是遗漏** —— 这一版最容易引起"为什么 YAML 没有 `Dispose`、
为什么 MsgPack 没有 `Write*Property`"的疑问，答案全在第 5 节。

## 1. 为什么是 x 而不是 y

版本规则写在 `scripts/release.ps1` 的注释里，原文两行：

```
x bumps when the public API changed (y resets to 0)
y bumps when it did not
```

**判据是"公开面变没变"，不是"谁会被打断"。** 工具比的是新导出的公开面与 `api/*.public.txt` 这份
"**上一次发布**的表面"之间的差集，`+N / -0` 也是 changed —— 加一行公开面，读者看到的就是一个更大的 API，
所以它走 x，`y` 归 0。本版实测（三行 `changed` 来自三个不同的包，这是本版最要紧的一条：**不是只有 JSON 变了**）：

```
   PicoJetson: API changed (+10 / -0)
   PicoMsgPack: API changed (+3 / -0)
   PicoYaml: API changed (+7 / -0)
   ...
   API changed  : true
   next version : v2026.13.0
```

同一把尺子的另一半就是上一个版本：`v2026.12.1` 的 11 个包**一行未动**，因此 `API changed: false` ⇒ `y + 1`。
两个版本合起来才是这条规则的全貌 —— **y 是"公开面没变"，x 是"变了"，不含贬义**；
"破坏性"与"纯新增"的区分写在正文（第 0 节的表），不在版本号里。

## 2. 本版解决的成因（两条，各自一段）

### 2.1 成因一：「名字 + 值」无法一次写完 ⇒ helper 必须 `ref` ⇒ 传错静默丢字节

写一个成员过去（今天也仍然可以）是**两次调用**：

```csharp
w.WritePropertyName("name"u8);
w.WriteString(value);
```

两次调用之间就是错误的容身处，而每个下游作者都会走到同一个地方：既然每次都要写两行，就写一个 helper 把它包起来。
**这个 helper 必须取 `ref JsonWriter`** —— span 游标是 `JsonWriter` 的一个**值字段**，按值传参是复制，复制写进同一段
内存、但它自己的提交永远不会跑，于是那段字节**静默消失**：`JsonWriterSpanCacheTests.PassingTheWriterByValueLosesTheValueWrittenThroughTheCopy`
钉住按值传参输出 `[]`，而欠的是 `[42]`，**不抛**；全仓静态闸 `JsonWriterSpanCacheTests.NoSourceFilePassesTheWriterByValue`
扫过每一个 `.cs` 文件，禁止任何地方按值取 `JsonWriter`。`MsgPackWriter` 是同一个形状（`_span` + `_spanPos`，第 5 节），
按值传同样一个字节都留不下。

代价不是"理论上可能"，是**两代下游各自的实测**（`3cd666f` 的消息，与 `PicoJetson/src/PicoJetson/JsonWriter.cs`
里那段同名注释的原文）：**2026.10 丢的是分隔符，2026.11+ 丢的是整个成员**，**两代都不抛**。错误唯一能住的
地方就是 helper 的签名，而签名不会报错。

所以根绝方式不是"再写一份更小心的 helper"，是**把那一对从调用方手里拿走**：一个调用不可能被拆开，
也就没有地方放这个错。本版把这七次合并**同时**给了两个有这种成对语法的格式（JSON 的 `"a": value`、YAML 的 `a: value`），
`3cd666f` 与 `d403694` 各一次，成员名单逐字相同（第 3 节）。

### 2.2 成因二：「我写完了」无法表达 ⇒ `Flush()` private、唯一提交点是 `End*`、没有 `Dispose` ⇒ 早退丢尾部

`Flush()` 过去是 **private**，`JsonWriter` 上唯一说得出"交出去"的调用是最外层的 `WriteEndObject` /
`WriteEndArray`（`depth` 回 0 的那一刻）。`Dispose` 没有，`Complete` 没有，`using` 也就写不出来
（`ref struct` 曾经连作用域钩子都没有）。于是每一次从容器里的提前 `return`、每一个从容器里抛出的异常，
都把尾巴留在 span cache 里：小文档只剩 `{`（1 字节），40 个成员的大文档停在最后一次 256 B 刷新
（`PicoJetson/README.md` → "### Closing a container is the commit point" 实测 **502 B**，收尾是 `,"prop":`），
**不抛**，`PicoDocument.IsValid` 报 `false`。

本版让这句话第一次说得出，两个成员各答一半，**都不关容器、都不抛**：

- `Flush()` —— "**把我写到此为止的交出去**"，容器保持打开，字节仍是文档的合法前缀，调用方可以接着写；
- `Dispose()` —— 同一个提交，加上作用域钩子，于是 `using var w = new JsonWriter(buf);` 在**正常路径、
  提前 `return`、异常展开**三条路上都提交。

**`Dispose()` 不抛是设计上的必要条件，不是宽容**：它会在一场已经在展开的异常里运行，一个会抛的 `Dispose`
会把它存在的那条路打断；而一个会"补一个 `}`"的 `Dispose` 要么产出非法的 `{"a":}`（属性名挂着还没值），
要么对"我还没写完"的调用方撒谎。所以 `using` 是安全的：**它不会因为容器没闭合而抛**，你拿到的是自己写的那些
字节 —— 闭合了就是一份合法文档，没闭合就是一份诚实的半成品。

**这条在第二个 span-caching writer 上不是类比，是同一条（`396076e`）。** `MsgPackWriter` 同样把字节存在
`_span`/`_spanPos` 里，同样只有一个"提交出口"（`public IBufferWriter<byte> Buffer` 这个 getter 的副作用 ——
一个消费者看得见的成员里，说"提交"竟然要去读一个属性），而且它连"最外层 `End*`"这条路都对裸值不成立：
一个没有容器的值**永远不会**被提交。它欠的东西和 JSON 一模一样，所以拿到的两个成员也一模一样（第 5 节）。

### 3.1 语义，一句一条

| 成员 | 语义 |
|---|---|
| `JsonWriter.Flush()` / `MsgPackWriter.Flush()` | 把 span cache 里挂起的字节提交给 `IBufferWriter`。**不关容器**（不发明括号 / 不发明 map 终止符、不动 `depth`），**从不抛**。之后 `BytesWritten == buffer.WrittenCount`，并且**把 span 丢掉**（缓冲已经有了那些字节，留着它下一次写就会写进已提交的内存 ⇒ 重复字节 / 损坏） |
| `JsonWriter.Dispose()` / `MsgPackWriter.Dispose()`（`IDisposable`） | 与各自的 `Flush()` **同一个提交**，加一个作用域钩子。**提交、不关容器、从不抛**；幂等；**不结束 writer 的命**（只清 span cache，之后再写会重新取 span 继续）。对 MsgPack 来说"关容器"根本不可表达：map 的成员个数写在**头里**，那个字节早就提交了 |
| `WriteNullProperty(ROS<byte> name)` | JSON 写 `"name":null`；YAML 写 `name: null` |
| `WriteBooleanProperty(ROS<byte> name, bool)` | `"name":true\|false` / `name: true\|false` |
| `WriteNumberProperty(ROS<byte> name, int)` / `(…, long)` / `(…, double)` | `"name":<数字>` / `name: <数字>`，走既有的 `WriteNumber` 兄弟 ⇒ invariant 格式化、`NumberHandling`（NaN / ±Infinity 与 Strict 下的异常）都是兄弟的，不是第二份实现 |
| `WriteStringProperty(ROS<byte> name, ROS<byte> utf8Value)` | 值已预编码为 UTF-8 |
| `WriteStringProperty(ROS<byte> name, ROS<char> value)` | 值给 UTF-16 文本 |

**整族的合同是两条**（JSON 侧 `JsonWriterPropertyHelperTests`、YAML 侧 `YamlWriterPropertyHelperTests` 逐条钉）：

1. **字节同一**：每一处合法使用，输出与 `WritePropertyName` + `WriteX` **逐字节相同** —— 分隔符、转义、缩进、
   数字格式、失败行为都是（它**委托**给兄弟，不重新暂存字节）。压缩与缩进两种形态都测，JSON 10 种形状、
   YAML 15 种形状（含超过栈缓冲的 300 字符值 / 300 字节名，YAML 那侧以十六进制比对，差一个空格都会红），
   外加 de-DE 下的文化不变性。
2. **JSON 有、YAML 没有的那条守卫**：JSON 的七个成员**必须有一个对象** —— 根位置或数组元素位置，
   `"a":` 根本不是 JSON，所以在**任何字节入栈前**就抛 `InvalidOperationException`，而两调用形式过去会把
   裸成员**静默**写出去。这是整族**唯一**的收窄。**YAML 侧故意没有这条守卫**：YAML 的根**就是**一个 mapping
   （`a: 1` 在列 0 是一份合法的单行文档），拒绝它等于拒绝格式能表达的东西；而且 `YamlWriter` 只记 `depth`、
   不记容器**种类**，要分辨"mapping 位置 / sequence 位置"就得发明它本不需要的状态 —— 那正是"复用既有路径"禁止的。
   `YamlWriterPropertyHelperTests.RootLevelMember_IsALegalDocument_AndIsNotRefused` 把这个差异钉成断言。

**故意没有的**（不是遗漏，是判定）：`float` **没有**孪生重载 —— 它会宽化进 `double` 重载，把 `0.1` 打成
`0.10000000149011612`，一个**安静的数字变化**恰是本版要消灭的那一类失败（JSON 与 YAML 同一理由，两边都测了 NaN
的异常类型与消息来自兄弟）；`decimal` / `Guid` / `DateTime` 与其余数值种类是同一个理由的弱化版（只影响面、不错字节），
暂不加。拿着这些类型的调用方继续用两调用形式，仍完全可用。

## 4. 迁移

**1）旧写法仍完全可用 —— 什么都不用做。** 本版是纯新增（`-0`），`WritePropertyName` + `WriteX`、
`try/finally` + 显式闭合、你自己那个 `ref` helper、`_ = mw.Buffer;` 这个靠 getter 副作用提交的老写法，
全部照旧编译、照旧跑出同样的字节（`MsgPackWriter.Buffer` 的隐含提交保留着，`396076e` 只删了 `internal` 的别名）。

**2）想更安全：把 `try/finally` 换成 `using`。** 两种写法今天都对，区别只在**异常路径**：

```csharp
// 过去唯一的写法：早退/异常都要靠 finally 记得闭合
var w = new JsonWriter(buf);
w.WriteStartObject();
try { /* ... 可能在容器中间 return 或抛 ... */ }
finally { w.WriteEndObject(); }     // 这一行就是提交点

// 本版：作用域结束就提交，三条路（正常 / return / 异常）都算
using var w2 = new JsonWriter(buf);
w2.WriteStartObject();
/* ... */
```

注意 `using` **不等于**"自动补 `}`"：它提交，不闭合。`Dispose` 时容器还开着，你得到的是那段诚实的前缀
（`{"a":1` 而不是 `{"a":1}`）—— 想让文档合法，仍然要自己 `WriteEndObject()`，只是不必再把它塞进 `finally`。
MsgPack 侧是同一句话、同一个形状：`using var mw = new MsgPackWriter(buf);` 之后，裸值、早退、异常三条路上的尾巴
都会交出去（第 6 节第 13–15 条）；**不闭合的 map 仍然是一份不完整的文档**，`Dispose` 只是不把它藏起来。

**3）自定义 helper 可以删掉，改用 `Write*Property`。** 这是本版的正题，不是风格建议：

```csharp
// 删掉：一对调用 + 一个必须 ref 的 helper = 出错时静默丢字节
static void Prop(ref JsonWriter w, string name, string v) { w.WritePropertyName(…); w.WriteString(v); }

// 换成：一次调用，拆不开
w.WriteStringProperty("name"u8, value);
w.WriteNumberProperty("count"u8, 42);
```

YAML 是同一替换（同一个类名、同一个成员名：`yaml.WriteNumberProperty("count"u8, 42);`），
`WriterPropertyHelperCrossFormatTests` 用**同一串成员调用**写两份文档、再用两个独立 reader 读回同一份模型来钉这件事。

**4）如果你保留自己的 helper，签名必须是 `ref`。** `JsonWriter` 与 `MsgPackWriter` 都是 `ref struct`，
字节游标是**值字段**，按值传 = 复制 = 复制里的提交永远不跑 ⇒ **静默丢字节**（`in` / `out` 也不行，按值更不行）。
JSON 侧有既有的实测（`[]` 而欠 `[42]`）与全仓静态闸 `JsonWriterSpanCacheTests.NoSourceFilePassesTheWriterByValue`；
MsgPack 侧本分支实测了同一形状：一个 `static void H(MsgPackWriter copy) => copy.WriteInt32(42);` 的 helper，
按值调用之后 `writerBytes=0 bufferWritten=0` —— **一个字节都没有留在缓冲里，也不抛**。
YAML 的失败形状不同、但不是"更安全"：它逐 token 直写，按值传时那些字节**确实会落进**缓冲（实测 `x: 1` 5 字节都在），
但**调用方那个 writer 的记账丢了**（`BytesWritten=0`、`_afterKey`/`_depth` 不再跟着变），后面接着写的分隔符
与缩进就由一份过期的状态决定 —— 拿到的是一份"字节在、状态不在"的 writer。所以三个 writer 的结论一样：
**helper 若要留，签名就写 `ref`**。这条规则不是本版新加的（静态闸一直在守 JSON），但本版是第一次让
"不写 helper"成为一个可行的选择。

**5）误用会抛（JSON 侧唯一的行为变化）。** `WriteStartArray()` 之后 `WriteEndObject()` 过去静默产出 `[}`，现在抛
`InvalidOperationException`（第 6 节第 1 条）。跑到就改调用顺序，**别 `catch` 掉** —— 它说的是你的括号记账
已经错了，而过去那份非法文档要等到下游才发现。

## 5. 谁有、谁没有 —— 这是设计决定，**不是遗漏**

二十行 delta 只落在三个 writer 上，而且是**逐 writer 对照过的结论**（`793990f` / `32d3808` / `396076e` / `d403694`
四个提交各带一张五 writer 的对照表），不是"只挑了三个做"的省略：

| writer | 有挂起字节吗 | `Flush()` / `Dispose()` | `Write*Property(name, value)` |
|---|---|---|---|
| `JsonWriter`（JSON） | **有**（私有 span cache） | ✅ **本版给了**（`32d3808`） | ✅ **本版给了 7 个**（`3cd666f`） |
| `MsgPackWriter`（MsgPack） | **有**（`_span` + `_spanPos`，`Ensure` 才落盘） | ✅ **本版给了**（`396076e`） | ❌ **按设计表不加**（成员写入形状不同，见下） |
| `YamlWriter`（YAML） | **没有**（逐 token 直写 buffer，实测 pending = 0） | ❌ **不需要**（没有可提交的状态） | ✅ **本版给了 7 个**（`d403694`） |
| `TomlWriter`（TOML） | 没有（逐 token 直写 buffer） | ❌ 不需要 | ❌ **不加**：已有 `WriteKeyValue(name, value)`；嵌套是 `[table]` 头 |
| `IniWriter`（INI） | 没有（逐 token 直写 buffer） | ❌ 不需要 | ❌ **不加**：已有 `WriteKeyValue(name, value)`；嵌套是 `[section]` 头 |

**"YAML 没有挂起字节"是实测的，不是读代码猜的。** 一个 out-of-tree 探针（临时目录，不进仓库，直接引用本分支构建出的
`PicoYaml` / `PicoMsgPack` / `PicoToml` / `PicoIni`）比较 `writer.BytesWritten` 与 `buffer.WrittenCount`：

```
YAML 只写了一个名字（半截成员）:      writerBytes=2    bufferWritten=2    pending=0   ["x:"]
YAML 写完两个成员、没有任何收尾调用:  writerBytes=21   bufferWritten=21   pending=0   ["name: Alice\ncount: 3\n"]
YAML 5000 字符的载荷:                writerBytes=5006 bufferWritten=5006 pending=0
MsgPack 一个裸 int 42:               writerBytes=1    bufferWritten=0    pending=1   → Flush() → 1/1
TOML 一个 key/value:                 writerBytes=6    bufferWritten=6    pending=0
INI  一个 key/value:                 writerBytes=7    bufferWritten=7    pending=0
```

`YamlWriter` 三例 `pending = 0`（连"只写了名字、还没写值"那一刻也是 0）⇒ **它没有第二个状态可以提交**，
`Flush`/`Dispose` 在它上面只能是一个空方法 —— 那和本版要修的病是同一个病（说了一件不成立的事）。
如果哪天真给它一个 `Flush`，那一定是因为它先有了 span cache，而不是因为别的 writer 有；**本版实测它确实没有。**

读法，四条：

- **`Flush()` / `Dispose()` 只加在"真的会挂起字节"的两个 writer 上**（`JsonWriter`、`MsgPackWriter`）。
  另外三个每写一个 token 就直接落进 `IBufferWriter`，给它们一个 `Dispose` 会是在描述它们并不持有的状态。
- **`Write*Property` 只加在"名字 + 值"是一对**、而且这一对之间**有可错配的标点**的两个格式上：
  JSON 的 `"a":` 与 YAML 的 `a:` —— 那对括号/冒号/换行正是 2026.10 与 2026.11+ 丢掉的东西。
  **MsgPack 不是这一类**：它的成员是"一个 key 字符串 + 一个值"，两者**背靠背**，中间没有冒号、没有分隔符、
  没有换行可以丢（`MsgPackWriter.cs`：`WritePropertyName(utf8Name) => WriteString(utf8Name)`）；
  map 的成员个数还是由 `WriteStartObject(count)` **在头里预先定死**的，一个成员不是可以事后追加的独立单位。
  设计表给 MsgPack 那一行的"名字 + 值入口"写的就是 `WritePropertyName` + `WriteStartObject(count)`，
  所以它拿到的是那对**提交出口**，不是这个**命名族**。这一条是判定，不是欠账（第 8 节也没有为它排队）。
- **TOML / INI 不加 `Write*Property`，两个理由各自都成立。** 其一，它们的一次调用入口已经是
  `WriteKeyValue(name, value)`，本版要消灭的那个"两次调用之间"从来没有存在过；其二，它们在**语义上**不是
  property —— 嵌套是 `[table]`（`TomlWriter.WriteTable`）/ `[section]`（`IniWriter.WriteSection`）的**头**，
  不是一个名字后面跟值。把一个 key/value 叫成 `property`，是在用一个别的格式的形状描述它们 —— 撒谎。
- **YAML 有"名字 + 值"的两次调用，但没有挂起字节**，所以它欠的是**命名族**，不欠作用域钩子 —— 本版两样都按这个
  判据给了：`3cd666f` 与 `d403694` 给两个格式同一个族，`396076e` 给第二个 span-caching writer 同一对出口。

这三条都写在提交里，不是事后补的解释：`571e1b5` 的消息结句是 "This commit closes the JSON hole; the same audit
for the other four is not claimed."，`396076e` 的判据是"类型里有 pending 状态就必须有成员说出来"，
`d403694` 的判据是"YAML 的根本来就是 mapping，所以**不加**守卫不是收窄，是格式事实"。
