## 2. 迁移：照着改就这三步

### 2.1 换枚举名，补一行 `using`

枚举换了**命名空间**，不只是换了名字。旧名字是随 `using PicoJetson;`（各格式各自的）进作用域的，新名字不是 ——
只把类型名替换掉、不补 `using` 的话，**`CS0103`**：

```csharp
// 旧：v2026.11.0，能编译
using PicoJetson;

var opts = new JsonOptions
{
    DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull,
};
```

```csharp
// 新：v2026.12.0
using PicoJetson;
using PicoSerDe.Core;   // ← 只加这一行；枚举在 PicoSerDe.Core 里

var opts = new JsonOptions
{
    DefaultIgnoreCondition = PicoIgnoreCondition.WhenWritingNull,
};
```

不想加 `using` 就写全限定名，两者等价：

```csharp
var opts = new JsonOptions
{
    DefaultIgnoreCondition = PicoSerDe.Core.PicoIgnoreCondition.WhenWritingNull,
};
```

`PicoSerDe.Core` 是五个格式包**本来就依赖**的那个包，所以这一步不需要新增任何 PackageReference。
本仓库自己的示例就是这么改的：`PicoJetson/samples/PicoJetson.Sample` 在换类型名的同时补了
`global using PicoSerDe.Core;`。

旧名 → 新名，逐格式：

| 格式 | 旧类型（已删除） | 新类型 |
|---|---|---|
| JSON | `PicoJetson.JsonIgnoreCondition` | `PicoSerDe.Core.PicoIgnoreCondition` |
| MsgPack | `PicoMsgPack.MsgPackIgnoreCondition` | 同上 |
| INI | `PicoIni.IniIgnoreCondition` | 同上 |
| TOML | `PicoToml.TomlIgnoreCondition` | 同上 |
| YAML | `PicoYaml.YamlIgnoreCondition` | 同上 |

### 2.2 语义对照：成员名没变，数值变了

| 成员 | 语义（新旧相同） | 旧数值 | 新数值 |
|---|---|--:|--:|
| `Never` | 不跳过（全局默认就是它） | `0` | **`1`** |
| `WhenWritingNull` | 值为 `null` 时跳过（只影响写侧） | `1` | **`2`** |
| `WhenWritingDefault` | 值为 `null` 或 `default(T)` 时跳过（只影响写侧） | `2`（**仅 JSON 有**） | **`3`** |
| `Always` | 该成员处处剔除（attribute 级语义） | 这五个枚举里**不存在** | **`0`**（新） |

**只改名字的代码不用管数值** —— 生成器与运行时不按数字比较，全是命名的常量比较（见
`api/PENDING-CHANGES.md` 里 "Why it is safe to merge into one enum"）。数值只在一种情况下咬人：

### 2.3 如果按数字持久化过这个枚举（配置 / DB / `(int)` 转换）

那么升级是**静默改变行为**，不会编译报错：

| 存下来的值 | `v2026.11.0` 的意思 | `v2026.12.0` 的意思 |
|--:|---|---|
| `0` | `Never`（全都写） | `Always` —— 作为 options 默认值仍然是"全都写"，但作为 `[PicoIgnore(Condition = 0)]` 现在**剔除**该成员 |
| `1` | `WhenWritingNull` | `Never` —— null 成员又被写出来了 |
| `2` | `WhenWritingDefault`（仅 JSON） | `WhenWritingNull` —— null 跳过，`default(T)` 写出来 |
| `3` | 不存在 | `WhenWritingDefault` |

修法二选一：把存量的数字按上表重映射，或者干脆改存**名字** —— 没有任何成员被改名，所以
`Enum.Parse<PicoIgnoreCondition>("WhenWritingNull")` 对所有历史值都仍然成立。

### 2.4 `Always` 作为全局默认值：接受但惰性

`PicoIgnoreCondition.Always` 是 **attribute 级**的"处处剔除"哨兵。作为 `DefaultIgnoreCondition` 它
**没有全局含义**：没有任何生成器实现"整类成员全剔除"，所以它落进 else 分支，行为等于 `Never`（全都写）。
方向是安全的（只可能多写，不会丢数据），但同名字反向语义容易读错，五个 Options 的 XML 注释现在都写明了这一点。

同理，`WhenWritingNull` / `WhenWritingDefault` 在 TOML/INI/YAML/MsgPack 上本来就是惰性的（那四种格式不实现
`WhenWritingDefault`，TOML/INI/YAML 连 null 字面量都没有），**升级前后一致**，不是本次引入的行为。

### 2.5 不用改的部分

- `[PicoIgnore]` / `[PicoIgnore(Condition = ...)]`：它们用的是 `PicoSerDe.Core.PicoIgnoreCondition`，**改动前后同一个枚举**，一行都不用动。
- **线上字节**：`v2026.11.0` 上就存在的设定，升级后逐字节相同（JSON 的 `WhenWritingDefault` 也一样）。新暴露出来的设定（INI/TOML/YAML/MsgPack 的 `WhenWritingDefault`、五个格式的 `Always`）实测等于各格式 `Never` 的字节 —— 新成员不会产生新的线上格式。
- 反序列化：忽略条件从来只影响写侧，读侧仍然映射这些成员。
- `PicoSerDe.Core` 的公开面：**没变**，所以不需要"先升级 Core 再升级格式包"的先后顺序。

## 3. 为什么标成破坏性（x bump 而不是 y）

1. **五个公开类型消失**。任何把 `JsonIgnoreCondition` 写进签名、字段、泛型参数、`typeof`、`nameof` 的代码，升级即 `CS0246`/`CS0103`。
2. **五个公开属性换类型**。`JsonOptions.DefaultIgnoreCondition` 从 `JsonIgnoreCondition` 变成 `PicoSerDe.Core.PicoIgnoreCondition` —— 属性还是那个属性，但显式标注类型的代码（`JsonIgnoreCondition c = opts.DefaultIgnoreCondition;`、参数类型是旧枚举的 helper、旧枚举上的扩展方法）全部断。
3. **反射 / 序列化元数据里类型名变了**。以程序集限定名持久化过类型（例如某些配置 binder、schema 文件、`Enum` 名字存库）的消费者，看到的是 `PicoJetson.JsonIgnoreCondition` → 找不到。
4. **数值漂移**（见 2.3）是"不报错的行为改变"，比编译错误更值得记一条。

按仓库的版本规则（`scripts/release.ps1`：有 delta 且**有删除** ⇒ x bump），`-DryRun` 自己算出来的就是
`v2026.12.0`。

## 5. 跨包兼容：同时引用兄弟包的消费者**不是** drop-in

前四节讲的是"**你自己**仓库里的代码怎么改"。这一节讲"**别人的包**怎么坏" —— 两者都会断，但断法完全不同：
你自己的源码是 `CS0246` / `CS0103`，**编译期**就红；兄弟包是**编译通过、启动才炸**，因为它是**按旧公开面编译好的二进制**。

### 5.1 一句话：属性 setter 就是一个方法签名

`PicoJetson 2026.12.0` 把 `JsonOptions.DefaultIgnoreCondition` 的类型从 `PicoJetson.JsonIgnoreCondition` 换成
`PicoSerDe.Core.PicoIgnoreCondition`（第 4 节第 1 行）。属性的 setter 在 IL 里是方法
`set_DefaultIgnoreCondition(枚举类型)` —— **类型换了，这个方法的签名就换了**。于是任何按旧签名编译出来的程序集，
都留下一个**指向已不存在方法**的调用点。

这类调用点**不是** NuGet 依赖解析能看见的东西：包元数据里没有"我编译时用的是哪个方法签名"这种信息。
结果就是 `dotnet restore` 成功 → `dotnet build` 成功 → `dotnet run` 时 `TypeInitializationException`。

### 5.2 受影响的包与最低配套版本

| 包（所在仓库） | 为什么受影响 | 最低配套版本 |
|---|---|---|
| **`PicoJsonRpc`**（`PicoNode` 仓库） | `PicoNode/src/Rpc/PicoJsonRpc/JsonRpcEnvelopes.cs:141` 写 `DefaultIgnoreCondition = JsonIgnoreCondition.Never`（**旧类型**），且落在 `JsonRpcCodec` 的**静态初始化**里 | **必须基于 `PicoJetson 2026.12.0`（或更高）重发**。已发布的 `PicoJsonRpc 2026.6.0`（NuGet 上最新的一版）与 `PicoJetson 2026.12.x` 组合**不兼容** |

**怎么找出其余受影响的包**：不看包名，看**引用点**。凡是引用下列任意一项的兄弟包，都必须基于 `2026.12.0` 重发：

```
JsonOptions.DefaultIgnoreCondition          （get 或 set，五个格式包各自一份）
PicoJetson.JsonIgnoreCondition              ┐
PicoMsgPack.MsgPackIgnoreCondition          │ 这 5 个类型在 2026.12.0 已删除：
PicoIni.IniIgnoreCondition                  │ 源码引用是 CS0246，
PicoToml.TomlIgnoreCondition                │ 已编译二进制引用是 MissingMethod
PicoYaml.YamlIgnoreCondition                ┘
```

在 `PicoHex/` 下全部兄弟仓库（`PicoActor` / `PicoAgent` / `PicoBench` / `PicoInfra` / `PicoNode` / `PicoUI`）
源码实跑这条 grep，**当前命中 1 处** —— 就是上表那一行的 `JsonRpcEnvelopes.cs:141`，其余五个仓库源码 **0 处**。

但这只说明**源码**没引用。完整判据是 **"发布过的二进制 × 编译它时的 PicoJetson 版本"**，不是"当前源码"：
某个包只要**曾经**用 `<= 2026.11.0` 编译并发上 NuGet，它的 dll 里就带着旧签名调用点，与今天的源码干净与否无关。

### 5.3 症状与判据（消费者怎么一眼认出）

**编译期没有任何信号。** 炸点在**第一次触碰 `PicoJsonRpc.JsonRpcCodec`** 的时候（静态构造里初始化 `Camel`），
例如一次 `JsonRpcCodec.Serialize(...)`。下面是**实跑复现**的输出（`PicoJetson 2026.12.0` + `PicoJsonRpc 2026.6.0`，net10.0）：

```
System.TypeInitializationException: The type initializer for 'PicoJsonRpc.JsonRpcCodec' threw an exception.
 ---> System.MissingMethodException: Method not found: 'Void PicoJetson.JsonOptions.set_DefaultIgnoreCondition(PicoJetson.JsonIgnoreCondition)'.
   at PicoJsonRpc.JsonRpcCodec..cctor()
   --- End of inner exception stack trace ---
   at PicoJsonRpc.JsonRpcCodec.Serialize[T](T value)
```

**三条判据，全中即是本问题**：

| # | 判据 |
|---|---|
| 1 | 异常是 `MissingMethodException`，且**外面包着** `TypeInitializationException`（不是 `NullReferenceException`，也不是 `JsonException` —— 升级本身不改线上字节，见 2.5） |
| 2 | 消息里的签名是 `Void PicoJetson.JsonOptions.set_DefaultIgnoreCondition(PicoJetson.JsonIgnoreCondition)` —— 参数是**旧类型 `PicoJetson.JsonIgnoreCondition`**。若参数写成 `PicoSerDe.Core.PicoIgnoreCondition`，那是另一个方向（见 5.5） |
| 3 | 栈里有 `PicoJsonRpc.JsonRpcCodec..cctor()`（静态构造），而不是某个业务方法 |

**不是**这些，别误诊：

| 看到的 | 其实是 |
|---|---|
| `CS0246` / `CS0103` | **你自己**源码引用旧枚举（第 2.1 节），编译期问题，不是跨包问题 |
| `MissingMethodException`，但签名或栈顶不同 | 另一处不兼容，按 5.2 的引用点清单重新查 |
| `InvalidOperationException: No serializer/deserializer registered for <>f__AnonymousType0...` | 跟跨包**无关**：`PicoSerDe` 不给**匿名类型**发序列化器。冒烟测试要用 `[PicoSerializable]` 的**具名**类型 —— 见到这条反而说明 cctor 已经过了，组合是好的 |
| `FileNotFoundException: Could not load file or assembly 'PicoJetson, Version=2026.12.0.0'` | 程序集版本**回退**（部署里放了更旧的 `PicoJetson.dll`），不是本问题 —— 本问题是**新程序集已加载、方法找不到** |

### 5.4 为什么版本号挡不住

NuGet 只在**依赖声明**上做约束，而 `PicoJsonRpc 2026.6.0` 声明的是一条**开区间下界**：

```xml
<!-- picojsonrpc 2026.6.0 nuspec, net10.0 -->
<dependency id="PicoJetson" version="2026.10.0" exclude="Build,Analyzers" />
```

NuGet 的写法里，**裸版本号 `version="2026.10.0"` 就等于 `[2026.10.0, )`** —— 下界、**无上界**。
所以 `PicoJetson 2026.12.0` **满足**这个约束，restore 照常挑最新，"两个包各自都装得上"。
NuGet 无从知道 `set_DefaultIgnoreCondition` 的签名变了：**没有任何元数据描述"这个包编译时面对的是什么公开面"**，
只有程序集版本号，而版本号里没有方法签名。

这不是谁忘了写约束，是**结构性的**。所以修法只能是：**兄弟包自己把下界抬到 `[2026.12.0, )`**，
用一次重发把"我编译时用的面 ≥ 2026.12.0"写进**新版本**的依赖声明：

```xml
<!-- 兄弟包重发时应当声明的形状：下界 2026.12.0，无上界。
     走 CPM 的仓库写 PackageVersion（`PicoNode` 就是这样），没走 CPM 的写 PackageReference，语义一样 -->
<PackageVersion Include="PicoJetson" Version="[2026.12.0, )" />
<!-- <PackageReference Include="PicoJetson" Version="[2026.12.0, )" /> -->
```

一句提醒，免得把方括号当成魔法：`[2026.12.0, )` 与裸写 `2026.12.0` 在 NuGet 里**语义相同**（都是"最小
2026.12.0、无上界"）。真正起作用的是**把下界从 2026.10.0 抬到 2026.12.0**，方括号只是把这个下界写明白。
下界抬上去以后，两个方向的处理并不对称：

- **旧方向的坑挡不住**（旧二进制 + 新 `PicoJetson`）：已发布 `PicoJsonRpc 2026.6.0` 里那条 `>= 2026.10.0` 是**历史事实**，
  改不了 —— 只能靠重发一个下界更高的新版本，让消费者去装它。
- **反方向挡得住**（新二进制 + 旧 `PicoJetson`）：新包声明 `>= 2026.12.0` 之后，NuGet 根本不会给你配出
  `PicoJetson 2026.11.x`（解析失败 / `NU1605`）。这是下界唯一能"自动生效"的方向。

### 5.5 一行迁移指引

**升 `PicoJetson` 到 `2026.12.x` 时，必须同时把 `PicoJsonRpc` 升到"基于 `2026.12.0` 重发的那一版"；做不到，就两个都别升。**

| `PicoJetson` | `PicoJsonRpc` | 结果 |
|---|---|---|
| `2026.11.x` 及更早 | `2026.6.0` | ✅ 可用（**实测**：`OK: {"a":1}`，PicoJetson `2026.11.0`；今天仍在用的组合） |
| **`2026.12.x`** | **`2026.6.0`** | ❌ **运行期 `MissingMethodException`**（5.3 那段输出）—— 就是这一格 |
| `2026.11.x` 及更早 | 基于 `2026.12.0` 重发的新版 | ❌ 装不出来：新包下界是 `[2026.12.0, )`，NuGet 拒绝降到 2026.11.x（源码层面也不可能：旧属性类型装不下新枚举） |
| `2026.12.x` | 基于 `2026.12.0` 重发的新版 | ✅ 目标状态 |

所以升级前先确认自己有没有这个传递依赖：

```bash
dotnet list package --include-transitive | grep -i PicoJsonRpc
# 有输出 ⇒ 只升 PicoJetson 会落进第 2 格；等 PicoJsonRpc 重发，或两个一起升
```

**只有纯 `PicoJetson` 用户（不引用任何兄弟包）** 才可以直接升 —— 那种情况读到第 2 节就够了。
