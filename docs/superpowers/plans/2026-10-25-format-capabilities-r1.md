# Format Capabilities R1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give PicoSerDe one testable source of truth for "which shape can which wire format express", make every dropped member report a diagnostic, and change **zero bytes** of generated code.

**Architecture:** 一处内部能力表（按**判定点**索引，值为三值效果 `Supported/DropMember/DropElement`）取代 25 处散落的格式字面量；形状通过一条有序「通路」穿过若干判定点，取最严效果。R1 只做**单一来源 + 消静默 + 诊断改造**，不改 wire 输出；能力放开在 R2。

**Tech Stack:** C# 13 / .NET 10, Roslyn incremental source generators, `shared/Gen` (linked into all 5 generators), TUnit + Microsoft Testing Platform, CSharpier.

**Spec:** `docs/superpowers/specs/2026-10-25-format-capabilities-design.md`

## 本计划的写法约定（先读这一节）

三轮复核暴露的 39 条问题里，超过一半是同一类：**计划用散文复述了代码事实**（某个函数允许哪些 kind、哪些行是格式特判、某个 csproj 有哪些属性），而这些复述会随代码漂移，且每次修都可能引入新的抄错。

因此本计划遵守两条规则：

1. **不复述可机械取得的事实。** 凡是「哪些行/哪些 kind/哪些属性」这类事实，一律**指向代码 + 给一条能跑出结论的命令**（见附录 A）。实现者用命令核对，而不是逐字照抄计划。
2. **每个跨任务使用的符号，必须在某个任务的 Interfaces 里定义过。** 计划里出现但未定义的符号 = 计划缺陷。

> **实现者须知**：如果某一步让你「自己决定」，而计划没写这个决定 —— 那是计划的问题，**不要猜**：把它记进 PR 描述，按最保守（不改变 wire）的选项做，并在最后统一报给维护者。

## Global Constraints

- **R1 must not change generated bytes.** Every task's verification includes the byte-diff gate from Task 2; new diagnostics are allowed, new/removed generated code is not.
- Format facts come from the spec's §3 table, which was measured with independent implementations (`tomllib`, PyYAML) — do not re-derive them from the current code.
- `FormatCapabilities` and both tables are **`internal`**: `api/*.public.txt` must not change. Any diff there is a bug in this release.
- Diagnostics: ids `PICOSERDE001`–`PICOSERDE005` are a public contract; do not renumber. New messages keep a stable greppable prefix.
- Never silence: no `continue` may skip a member without adding to a skip list that is actually reported (R2).
- Build with `-m:1` (`dotnet build PicoSerDe.slnx -c Debug -m:1`); parallel builds have crashed with `MSB4166`.
- Zero warnings: `dotnet build` must end at `0 Warning(s) 0 Error(s)`. Test projects that deliberately contain unrepresentable models add `PICOSERDE004` (and after Task 5, possibly `001`) to `NoWarn`, following `tests/PicoSerDe.Integration.Tests/PicoSerDe.Integration.Tests.csproj:13`.
- Format changed files with `dotnet csharpier format <files>` (run `dotnet tool restore` once).
- No test counts in any document; state the command, not the total.

## Review Focus

The spec is a vision document; its silence is not permission. These are the failure modes most likely to bite, most likely first, each pinned by a test in the task that owns the code:

1. **A generated serializer that compiles but drops a member** — the shapes in Task 2's corpus are the only guard; if a rewire (Task 3) flips one drop condition, only the byte diff catches it.
2. **A capability read that silently changes behaviour** — `CanRepresent` values copied wrong (e.g. YAML marked as unable to hold null) would drop data that the format can express. Task 1's `CanRepresent` is the code form of spec §3; Task 2's probe measures independently and the two are cross-checked.
3. **Diagnostics that multiply** — reporting `PICOSERDE001` from three sites (Task 5) can emit the same member repeatedly; Task 5 asserts one diagnostic per (type, member).
4. **A message that misleads** — the current text says "cannot be represented by this format" for shapes the format can represent (Task 7 must distinguish fact from debt).
5. **A public API change sneaking in through an internal type** — `FormatCapabilities` leaking into a `public` signature would force an `x` bump; Task 4's architecture test plus the `api/*.public.txt` diff gate covers it.

### Task 0 (DONE — spike) : 能力模型定稿

**结论（已在 `tmp/spike` 分支用代码证明，70/70 格复现）**

- 表按**判定点**索引（13 个），不按形状索引；每个 (格式, 判定点) 的值是**三值效果**：
  `Supported` / `DropMember` / `DropElement`。**不是** (allows?, granularity-if-blocked) 两字段 ——
  该形状表达不了「发成员但丢元素」（YAML 的 null 元素正是这种）。
- 每个形状对应一条**有序通路**（它要经过哪些判定点），取**最严效果**。通路里只放**必要条件**；
  `ArrayOfTables` 这类「某格式的实现方式」**不进通路**（否则会把 `S2×JSON` 判死）。
- 判定点（spike 里 13 个，Task 1 收敛为 **12** 个）：
  spike 的 `ExtendedKindResolves`、`ExtendedKindAsElement`、`ScalarKindResolves`、
  `NestedScalarContainer`、`NestedObjectContainer`、`NullableValueLeaf`、`NullableRefLeaf`、
  `ObjectListInMember`、`DictValueCollection`、`RecursiveSelf`、`RecursiveMutual`（11 个，有值），
  **加** `ConcurrentDictResolves`（新增，`TKR:107`）；
  **减** `ByteArrayAsBinary`（编码选择，不是能力）、`DictKeys`（限制，不是三值效果 → 改为 `AllowedDictKeyKinds`）。
- 通路（14 形状）：`S1=[]`、`S2=[ObjectListInMember]`、`S3=[NestedScalarContainer]`、
  `S4=[NestedObjectContainer]`、`S5=[NullableValueLeaf]`、
  `S6=[NestedScalarContainer,NullableValueLeaf]`、`S7=[ExtendedKindResolves]`、
  `S8=[NestedScalarContainer,ExtendedKindAsElement]`、`S9=[]`、`S10=[DictValueCollection]`、
  `S11a=[RecursiveSelf]`、`S11b=[RecursiveMutual]`、`S12=[NullableRefLeaf]`、`S13=[NullableValueLeaf]`。
- **三处拆分是被观测逼出来的，不是设计出来的**（这是本 spike 的主要价值）：

**`Facts`（格式事实，来自 spec §3）**：`bool CanRepresent(string fmt, string shapeId)` ——

**`TargetRules` 的推导规则**（对每个 判定点 × 格式）：
```
target(d, fmt) = Supported  当且仅当  ∀s ∈ ShapesUsing(d) : Facts(fmt, s) == 可表示
```

**校验**（这就是可执行定义）：
```csharp
[Test]
public async Task Target_is_supported_exactly_where_every_affected_shape_is_representable()
{
    foreach (var d in Enum.GetValues<Decision>())
    foreach (var fmt in FormatCapabilities.AllFormatTags)
    {
        var allRep = FormatCapabilities.ShapesUsing(d).All(s => FormatCapabilities.CanRepresent(fmt, s));
        var target = FormatCapabilities.DecideTarget(fmt, d);
        if (allRep) await Assert.That(target).IsEqualTo(Effect.Supported).Because($"{d}x{fmt}");
        // 否则：目标不高于现状（不强制等于，因为现状可能是 DropElement 且目标是 DropMember）
        else await Assert.That(target).IsNotEqualTo(Effect.Supported).Because($"{d}x{fmt}");
    }
}
```

**注意两处「目标 = 现状」的判定点**（编码差异，不是能力差异，必须在注释里写明，否则后人会"修正"它）：
`ScalarKindResolves`、`ConcurrentDictResolves` —— 它们只影响**编码形式**（是否走 json 的特化标量），不影响能否表达。
  - `RecursiveSelf` / `RecursiveMutual`（**Rules 现状值，不是目标值**）：`Self` 在 toml/yaml/ini 都是 `DropMember`；`Mutual` 在 toml 是 `Supported`（会发射，D-5 的根覆盖就发生在这里）、yaml/ini 是 `DropMember`。目标值由 Step 3 的推导规则算出，**不要**在这里手抄。
  - `ScalarKindResolves` / `ConcurrentDictResolves`：**保持现状**（编码差异，不是能力差异 —— 在注释里写明，否则无人知道为什么目标值= 现状）

  ```csharp
  [Test]
  public async Task Readme_matrix_cells_match_the_tables()
  {
      // README 只有 5 行形状且无 S-id：夹具把「描述前缀」映射到 shapeId
      var fixtures = new (string Prefix, string ShapeId)[]
      {
          ("| `List<Dto>`", "S2"),
          ("| `List<List<int>>`", "S3"),
          ("| `List<List<Dto>>`", "S4"),
          ("| `List<List<int?>>`", "S6"),
          ("| Recursive member", "S11a"),
      };
      var rows = File.ReadAllLines(Path.Combine(TestRepo.Root(), "README.md"));

      foreach (var (prefix, shapeId) in fixtures)
      {
          var row = rows.FirstOrDefault(l => l.StartsWith(prefix));
          await Assert.That(row).IsNotNull().Because($"README 缺少 {shapeId} 的那一行");

          // 单元格 = 第 2..6 段（第 1 段是行首竖线，第 7 段是行尾）
          var cells = row!.Split('|').Skip(2).Take(5)
              .Select(c => c.Trim().Length == 0 ? '?' : c.Trim()[0])
              .ToArray();
          var expected = FormatCapabilities.MatrixCells(shapeId)      // "✅✅✅✅❌" 这样的 token 串
              .ToCharArray();
          await Assert.That(new string(cells)).IsEqualTo(new string(expected))
              .Because($"README 的 {shapeId} 行单元格与表不一致");
      }
  }
  ```
  `MatrixCells` 因此**只返回 token 串**（`"✅✅✅✅❌"`，5 个字符），不含竖线与空格。
