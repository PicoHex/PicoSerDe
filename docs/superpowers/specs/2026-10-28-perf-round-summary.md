## 1. 一句话结论

归因分析给出的**六条主因**全部落地（JSON 三条、MsgPack 三条），期间修掉**两个真实正确性 bug**
（MsgPack timestamp-64 字段序、strict 测试因按值复制 `ref struct` 而空转）与**两条时间敏感的
假阳性测试**。代价有三条，都写在这里：MsgPack 往返会把 `DateTimeKind` 归一为 `Utc`（规范固有）；
按 **17:49–18:24** 窗口的最终数据，落后只剩 **4 格** —— **JSON JIT 3 格 + MessagePack JIT 1 格**（§7），
而这 4 格主要是**对手的分层编译红利**而不是我们的代码缺陷（§11）；JSON JIT 的中位仍读 **0.96×**。
反过来，**JSON AOT 已经 12/12 领先**（中位 **0.79×**、上界 **0.98×**），上一版这里的"9/12 慢"不成立。
今天还修掉一处**探针生成基线漂移**（`8ecdf4e`），并把"块字面量 vs 拼接字符串"的**行尾陷阱成类消灭**（`bbb94c4`，见 §5）。

## 4. 被否决的修法及理由

| 曾考虑 | 为什么否决 |
|---|---|
| 把 flaky 断言 `>` 改成 `>=` | 会消失，但测试从此**发现不了"返回常数"** —— 它唯一存在的理由。改法是抽出纯函数，而不是弱化断言 |
| MsgPack 保留 ISO 字符串写侧 | 放弃 65% 的 DES 收益与全部互操作；且它会让 msgpack 成为库里**唯一不能与生态对话**的格式 |
| 为免分配走"栈编码"或"经 `Buffer` 交接" | 实测**收益为 0 或更慢**（`perf-mp-str/report.md` §6.2） |
| 给 `FlushToBuffer` 改 `api/` 基线 | 基线记录**上次发布的面**，手改等于伪造发版 diff；正解是改成 `internal`，生成代码经既有的 `Buffer` 出口交接 |
| 手工合并生成代码基线 | 基线应由**合并后的生成器重新生成**；手工拼会掩盖生成器的真实输出 |

## 5. 修掉的真实 bug（不是性能）

| bug | 现象 | 为什么差点漏掉 |
|---|---|---|
| `timestamp64` 字段序 | 规范载荷（秒 = 1）解成 **1992 年** | 自写自读**能往返**（两边用同一位序）⇒ 只有规范测试或互操作才能发现 |
| strict 测试的 `BuildMap` **按值复制 `ref struct`** | 载荷 6 字节被截断成 **2 字节**（`81 00`） | 两条测试只断言"抛 `FormatException`"，而截断的输入**同样**会抛 ⇒ 测试空转 |
| flaky ①（校准） | 全量测试 **1/26** 概率红 | 断言依赖真实计时，只在机器忙时失败 |
| flaky ②（预热超时） | 4× 超订时 **7/10** 红 | 断言的是"预算里能跑几个 burst"——吞吐量事实 |
| **探针生成基线漂移**（两份 MsgPack 生成文件） | 入库基线仍是"逐元素循环"的形状，生成器已改成"批量调用 + 同一循环作回退"⇒ 重建探针 `diff -r` 出 **2 个文件** | 合并批量读的那次只验了 **wire 格**（70 格逐行相同，wire 一个字节没动），没验**生成文本**。生成文本只有"重建 + diff"才看得见（`8ecdf4e`） |
| **"块字面量 vs 拼接字符串"的行尾陷阱** | **两次假红**：CRLF 检出上 `"""…"""` 期望值每行多一个 `\r`，而实际值是 `string.Join("\n", …)` ⇒ 一次报 **163 个用例**（`e89bfd7` 的语法语料）或**整块期望值**（`8cd6a8c` 的冷抛块），而打印出来的两边**逐字相同** | 写它的工作树是 **LF** ⇒ 绿。**绿的是检出，不是被测代码**。两次都靠"打印长度、找末尾 `\r`"才诊断出来。今天用 `shared/TestText.cs` **成类消灭**（`bbb94c4`，merge `0601e20`）：全仓 83 个多行 raw literal 里只有 **2 个**是"被比较的期望值"，两边归一化后比较，且辅助函数自带一条"真差异仍必须红"的测试 —— 否则它会把真差异一起吃掉 |

## 6. 能力变化与取舍

**MsgPack 往返后 `DateTimeKind` 归一为 `Utc`。**

- **为什么**：timestamp 扩展的载荷只有「秒 + 纳秒」，即一个**瞬时**，规范里**没有 Kind 位**。
- **影响到什么**：`Unspecified` / `Local` 读回成 `Utc`；`Local` 是**转换**（`ToUniversalTime`），
  **tick 不变**，没有任何瞬间移动。
- **竞品同样如此**：MessagePack-CSharp 读同样字节省同样给 `Utc`（逐 tick 断言见
  `PicoMsgPack/tests/PicoMsgPack.Tests/TimestampInteropTests.cs`）。
- **代价的呈现方式**：能力探针 4 行 `OK → MISMATCH`（cell `S2`/`S4`，observation `S14`/`S15`），
  规格表 §3 写明原因，**没有**让基线偷偷同意。
- **替代方案**：保留 ISO 字符串 ⇒ 放弃 65% 收益与互操作（见 §4）。

**公共 API**：本轮登记了 4 条纯新增（`MsgPackWriter.WriteString(ReadOnlySpan<char>)`、
`WriteDateTime`、`MsgPackDateTimeFormat` 枚举、`MsgPackOptions.DateTimeFormat`），
全部记在 `api/PENDING-CHANGES.md`，`api/*.public.txt` **保持"上次发布的面"不动**。

### 7.2 落后的形状：一处，而且不是算法

三格 JSON 落后的都是**"按属性数放大"的对象/成员形状**（50 字段的读、50 字段的写、7 属性的读），
而三格在**同一窗口**的 `TC=0` 口径下**全部变领先**（0.73× / 0.56× / 0.74×）。
主因写在 §11：对手把默认分层编译换成 **×1.97** 的吞吐，我们只换到 **×1.14**。
MessagePack 那 1 格 1.12× 只比带边多 2 个百分点（同形状见 §7.1 注）。

**这不是免罪符**：用户跑的就是默认 JIT，发布口径的 **1.33× / 1.27× / 1.14× / 1.12×** 才是他真正拿到的数。

### 7.3 测量条件（本窗口）

单机、三轮取中位、AOT 与 JIT **各自独立进程**、共享桌面而非空闲实验机。本窗口 **39 个进程全部完成**、
**38 kept / 1 VOID**（`msgpack-jit` 第 6 轮 **31.2 %** 臂被拒 ⇒ 改名 `.refused.txt`，不进任何中位）、
**33 / 882 臂**（3.7 %）被负载判据拒绝、**12 个进程**在 `PICOBENCH_STRICT=1` 下以 `1` 退出、
10 次 precheck **全部一次通过**（中位 1.5 %–20.0 %）。每条发布的数字都建立在**三个未被拒的轮次**上
（10 行因某轮少一臂而用后续 kept 轮补，逐行点名见 `remeasure-5/report.md` §2.2），
被拒的臂在聚合表里**点名**而不是悄悄平均掉。本窗口整机比上一轮**快** 9 %–21 %（两臂同向）

## 10. 补充：契约工程（fused token reader）与重测结果

### 10.1 为什么会有这一节

§1 的"六条主因"解决之后，README 里 JSON 当时仍有 9/12 行落后于 System.Text.Json（那是本节开工前的情形；最终值见 §7）。做归因时发现原因不是某个局部热点，
而是 **`ITokenReader` 的两段式契约**：`Read()` 先分类字节，`TryGetX()` 再解码一次 —— **同一个字节被 switch 两遍**。
对比的参照物是 MemoryPack（分析见 `.superpowers/sdd/memorypack-analysis/report.md`）：它快是因为**wire 里没有需要分类的东西**，
我们不可能取消 tag，但可以让 tag **只被 switch 一次**。

契约在 Core 里，影响五个格式，所以按 spec → plan → 逐任务执行（`docs/superpowers/specs/2026-10-28-fused-token-reader-design.md`、
`docs/superpowers/plans/2026-10-28-fused-token-reader.md`）。

### 10.2 机制在第一个任务就被证伪了两次

| 尝试 | 结果 |
|---|---|
| **DIM（默认接口实现）** | **30 个 CS9245**：`ref struct` 必须自己实现接口全部成员，即使有默认体 |
| **扩展方法** | 编译能过 —— **但那个形状是静默错**：`this T reader` 按值传，`Read()` 推进副本 ⇒ **死循环** |

最终机制：**派生接口 `IFusedTokenReader` + Core 静态参考正本 `TokenReaderFused`**（六个 `ref T` 方法，只存在一份）。

> **这一节最值得记的不是机制，而是顺序**：因为先写 spec，错误在**第一个任务**暴露，代价约等于零；
> 若直接开工，会在五个格式上各改一遍之后才发现。

| `LargeFlat 50-fields — Deserialize` | **1.26×** | **2.28×** | 1.006× / 1.602× |
| `Complex POCO — Deserialize` | **1.23×** | **2.08×** | 1.071× / 1.670× |
| `LargeFlat 50-fields — Serialize` | **1.20×** | **2.22×** | 1.109× / 1.797× |

（来源：`.superpowers/sdd/json-jit-gap/report.md` §1.2。）读法：**对手把默认分层编译换成 2.08–2.28× 的吞吐，
我们只换到 1.20–1.26×**，差额几乎全在 tiering 那一层 —— 我们的 tier-0 代码和 tier-1 代码一样快，
所以分层管线对我们几乎什么都不做。MessagePack 那一格是同一个形状：对手 **2.18×**、我们 **1.15×**
（`mp-col-jit/report.md` §1.3，基线 `ac75ce0`）。

### 11.3 旁证：我们自己的绝对成本在 `default` 下**最低**

| 同一行的四种环境 | 我们 µs | 排序 |
|---|---|---|
| `remeasure-5` 本窗口 | default **2.654** · `TC=0` 2.891 · `PGO=0` 2.954 · AOT 3.356 | default 最便宜，AOT 最贵 |
| `json-largeflat` 专项复跑（3–6 次运行，CONTROL 0.99–1.01） | default **2.605** · `PGO=0` 2.942 · AOT 3.085 · `TC=0` 3.149 | default 最便宜 |

（来源：`remeasure-5/report.md` §7；`json-largeflat/report.md` §2.1。）
两条独立窗口给出同一件事：**AOT 在我们身上从不比 JIT 便宜**，JIT 也从不是"编译得更差"。
两个窗口里 `TC=0` 与 AOT 的先后顺序**相反** ⇒ 这两者之间不做方向声明。
所以 JIT 列读 1.33× 不是"我们的代码在 JIT 下坏掉了"，而是**对手在 JIT 下更便宜**。

### 11.4 结论（这张表要怎么用）

1. **JIT 列的差距大部分是对手的优化器红利，不是我们的代码缺陷**：三格在 `TC=0` 下全变领先
   （0.73× / 0.56× / 0.74×），在 AOT 下也不慢（`LargeFlat DES` **0.98×**、`Complex DES` **0.94×**、
   `LargeFlat SER` **0.92×**，`remeasure-5/report.md` §4.1）。
2. **但它不是免罪符**：用户跑的是默认 JIT，**1.33× / 1.27× / 1.14× / 1.12×** 就是他拿到的数，发布的就是这个。
3. **能拿回的部分只在分词器**：`json-largeflat/report.md` §2.3 把分词器定价为整行 **66 %（JIT）/ 74 %（AOT）**，
   但 `json-jit-gap/report.md` §7 明说 **29.3 ns/token 里只有约一半被单独定价** ⇒ 未归因就动手 = 赌博，本轮**没动**。
4. **口径本身也要发出去**：README 的 `### What the JIT column is comparing` 与本节是同一件事的两种写法 ——
   同一行三态并列，而不是只给最漂亮的那一个数。

### 12.1 属性站点融合（MsgPack 标量成员站点）：两轮实验方向相反，**最终判否、未合入**

T11（MsgPack E-3 元素循环融合）的同族提案：把对象成员的值读取也换成融合读
（`reader.TryReadInt32(out v)` 取代 `reader.Read()` + `reader.TryGetInt32(out v)`）。它**没有合入**，
理由是两轮实验互相矛盾，而**更紧的那一轮判否**。

| 项 | 内容 |
|---|---|
| **改了什么** | 生成器在**属性站点**发射融合读：`MsgPackSerializerGenerator.cs` 的四处调用点中三处（主 `Deserialize` 的成员循环、内联内部对象、内联嵌套对象）把循环顶部那句 staged `reader.Read()` 删掉，改由每个 `case` 自己推进；多态（string-key）与流式路径**不动**。分支 `feat/mp-prop-fused`，两个提交 `d1b3337`（发射 + 刷基线与中文摘要）→ `1196365`（回退），树与基点 `a3528cc` **逐字节相同** |

| **第二轮实测（真实发射）** | `feat/mp-prop-fused`：A = 基点生成的发射、B = 本分支生成的发射、C = **A 的逐字节副本**（CONTROL）。发布口径下**没有任何一行改善超出噪声**（最好的是 `Complex` 0.9919，方向还反）；唯一超出噪声的是 `MTenInts DES`，**1.068 / 1.045 / 1.084（3 进程同号，慢 4.5–8.4 %）**，其 CONTROL 1.001–1.006；同码行 `Collection SER` 读 0.986 / 0.910 / 1.002，这就是台架地板。**AOT `MTenInts` 1.054 / 1.038 / 1.054（慢 4–5 %）**，角色互换 `0.971 / 0.963 / 0.966`（3/3 过闸）⇒ 两段式便宜 3–4 %、融合贵 3–4 %，**同号，不是"谁排在 A"的产物** |
